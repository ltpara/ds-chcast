# S20 地址簿共享密码设计（2026-11-14）

## 1. 状态与待决策

当前保存的连接密码只在本机 DPAPI 文件中，以 trust key 作为熵绑定目标设备；
服务端地址簿没有密码字段。换设备或把地址簿共享给同事后，密码不会跟随，因此
S20 的目标是提供可选的账号级同步与地址簿共享能力，而不是上传现有 DPAPI 密文。

本文提出两条可实现路线。推荐 **端到端设备密钥路线**，它要求用户接受一个产品
取舍：没有可信设备在线或恢复包时，服务器无法帮助恢复密码库。若必须保证服务器
管理员可恢复、重置或代管密码，则只能选择服务端托管路线，并明确服务器可解密。

在用户确认该取舍前，不修改协议、数据库或 UI。

## 2. 现状与安全边界

- `app/windows/viewer/viewer_bridge.cc` 的密码存储以 trust key 的 FNV-1a 名称寻址，
  内容由 Windows DPAPI 加密，熵为 `chast-viewer-password:<trust key>`；密码上限
  为 128 字节。
- DPAPI 的 CurrentUser 范围不能直接跨账号或跨机器解密，因此现有文件不能作为
  云同步载荷。
- 服务端地址簿目前同步 peer ID、名称、标签、备注、分组和修订，不保存密码或用户名。
- 地址簿共享已有用户、账号组和 Everyone 三种 ACL，可作为密码条目的授权来源；ACL
  只能阻止服务器继续分发新包，不能收回已经送达对方的明文知识。

## 3. 方案比较

| 方案 | 服务器能否读取密码 | 换设备自动恢复 | 共享同事 | 撤销语义 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 服务端主密钥加密 | 能 | 能 | 简单 | 可立即拒绝后续读取，但服务器仍可解密 | 仅在需要服务端托管/恢复时采用 |
| B. 端到端设备密钥 | 不能 | 需旧设备批准或恢复包 | 需属主设备为接收方封装条目密钥 | 拒绝后续读取；已获知内容无法抹除 | 推荐 |
| C. 只导出本地加密文件 | 不能 | 手动 | 手动传递 | 由接收方自行保管 | 不满足账号同步与共享体验，保持现状 |

不得采用“用账号密码派生服务器端密钥”并宣称为端到端加密。OIDC/LDAP 登录可能没有
本地密码，服务器也能对弱口令做离线猜测，因此该方案最多是服务端托管加密。

## 4. 推荐设计：端到端设备密钥

### 4.1 密钥层级

1. 每台查看器生成独立的 X25519 设备加密密钥，私钥只在本机 DPAPI 保护下保存；
   公钥在已认证账号会话中注册。它不与现有的 Ed25519 票据种子复用，使用独立的
   域分隔与存储文件。
2. 每个密码条目生成随机的 256 位条目密钥，用 AES-256-GCM 加密条目正文；正文包含
   登录用户名和连接密码，避免把用户名当作明文元数据泄露。
3. 条目密钥再通过 X25519 + HKDF-SHA-256 派生的包装密钥分别加密给每个获授权设备。
   因此服务器只看到密文、设备公钥、挂载目标和修订号。
4. 服务端只保存信封，不保存条目密钥或条目明文；所有加解密和重新封装都在查看器
   进程内完成。

### 4.2 数据模型

| 数据 | 服务端可见字段 | 服务端不可见字段 |
| --- | --- | --- |
| 设备加密密钥 | device ID、公钥、创建/撤销时间 | 私钥 |
| 密码条目 | owner、peer ID、revision、删除状态、创建/更新时间 | 用户名、密码、备注正文 |
| 条目密文 | format/version、nonce、ciphertext、认证标签 | 条目正文 |
| 接收方包装 | recipient device ID、临时公钥、nonce、wrapped item key | 设备私钥、解包后的条目密钥 |

建议固定 `format=chast-password-item`、`version=1`；单条正文沿用 128 字节密码上限，
用户名与密码合包后设 1 KiB 上限，每个账号最多 2000 个本地密码条目，防止把地址簿
变成任意对象存储。所有服务端字段都要校验长度、重复 device ID、格式版本和归属关系。

### 4.3 新设备接入

新设备注册自己的公钥只能取得本机新条目，不能自动解开历史条目。首个历史同步需要：

1. 新设备显示一次性的 X25519 公钥与短验证码；
2. 任一已解锁的旧设备批准该公钥；
3. 旧设备解包历史条目密钥，再为新设备生成包装并上传；
4. 服务器仅在校验旧设备属于同一账号且当前仍有效后保存包装。

如果用户没有任何可信旧设备，则必须使用事先导出的恢复包；否则密码库保持不可读。
这是推荐方案的明确取舍。恢复包不能包含服务器主密钥，只能由用户单独保管的恢复
口令解包，并应支持撤销/重新生成。

### 4.4 地址簿共享

共享以现有地址簿授权为闸门，但增加“共享密码”选项：

- 属主设备读取当前被授权用户的有效设备公钥，为每个设备分别封装条目密钥；
- 新成员或新设备只有在属主设备下次在线时才能获得包装，避免服务器代替属主解密；
- 撤销授权后，服务器立即删除/停止下发该接收方的包装并拒绝读取；属主设备下次在线
  时应轮换条目密钥并重新封装给剩余接收方；
- 已下载过密码的接收方仍可能保留旧值，因此 UI 必须把“撤销共享”说明为停止后续
  同步，而不是远程擦除；密码轮换由用户显式执行并提升 revision。

第一版可以只做个人账号同步，再按实际需求增加用户/组/Everyone 密码共享，避免把
ACL 成员变化的在线依赖一次性塞进所有场景。

## 5. 服务端托管备选

若产品要求服务器管理员能恢复密码，或无法接受“所有设备丢失即密码库丢失”，可采用
服务端托管路线：

- 服务端使用独立密钥加密条目，数据库只保存信封，密钥不进入源码或备份；
- 支持密钥轮换、备份恢复、管理员审计和紧急撤销；
- API 与 UI 明确标注“服务端可解密”，不能使用端到端加密文案；
- 仍不保存明文，且密码字段不进入普通日志、CSV、管理台列表或错误响应。

这条路线实现更简单，但把数据库备份、服务器 root、运维人员和密钥管理器都纳入
密码的信任边界。对远控连接密码而言，默认建议选择端到端路线。

## 6. 分期与验收

### 阶段 A：个人账号同步（推荐先做）

1. 设备 X25519 密钥生成、DPAPI 保存、注册/撤销与域分隔测试。
2. 条目 AES-GCM 信封、接收方 X25519 包装、版本和篡改拒绝测试。
3. 新设备配对批准、旧设备重封装、恢复包导入/导出和无旧设备失败路径。
4. 服务端账号隔离、配额、严格式解析、幂等 revision、删除墓碑与审计测试。
5. Flutter 设置入口、按设备开关、错误提示和中英文文案；默认不同步密码。

### 阶段 B：地址簿共享

1. 复用现有用户/组/Everyone ACL，但只有明确选择“共享密码”的条目才封装。
2. 授权新增、成员加入、授权撤销和组成员变化的在线/离线行为必须确定。
3. 轮换条目密钥后旧包装不能被服务器或客户端误用。
4. 双查看器测试：A 保存、B 同步、B 离线修改、A 撤销、A 轮换、B 再同步。

### 共通验收

- 服务端集成测试断言数据库中不存在明文密码、用户名或 DPAPI 密文；
- 错误响应、审计、日志、导出、内存转储边界不包含条目正文；
- 重放、调换设备、修改 receiver ID、截断信封和错误版本全部拒绝；
- 真实双机和 Windows 用户切换验收；至少一台设备不保留服务器主密钥；
- 真实错误恢复：DPAPI 失效、设备密钥丢失、旧设备离线、恢复包丢失。

## 7. 需要确认的唯一产品取舍

**是否接受“端到端加密，因此服务器无法恢复；新设备需要旧设备批准或恢复包”作为
S20 默认语义？**

- 若接受：按第 4、6 节先实现阶段 A，服务器不持有破解能力。
- 若不接受：选择第 5 节服务端托管，明确服务器可解密，并补齐密钥轮换与备份恢复；
  此时不能把功能宣传为端到端加密。

在确认前，S20 保持“设计完成、实现待批准”，不把密码加入现有地址簿字段。
