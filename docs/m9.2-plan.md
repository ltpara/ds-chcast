# M9.2 — 多文件与文件夹传输

更新时间：2026-10-24
分支：`feat/m7-security`
基线：M9.1 完成（协议 v21；会话内画质/帧率/编码器偏好）。
本阶段将协议升到 v22。
参考：`D:\rustdesk` @ `c7f212d`（只做能力对照，不复制实现）

## 1. 范围与取舍

M9.1 之后，文件传输仍是一次一个文件：拖放只取第一个条目，文件选择器只能单选，
每次发送结束才能再选下一个。M9.2 把这条链路补齐为：

| 能力 | 行为 |
| --- | --- |
| 选择器多选 | `GetOpenFileNameW` 加 `OFN_ALLOWMULTISELECT`，一次加入多个文件 |
| 拖放 | `WM_DROPFILES` 取回全部条目，文件和文件夹都可以拖 |
| 文件夹 | 递归展开为“相对目录 + 文件名”的多个条目，主机在接收目录下重建子目录 |
| 发送队列 | 多个文件排成一条顺序队列；一个完成后自动开始下一个 |

不做的部分：

- **不做并行传输。** 传输层本来就按 transfer id 支持最多 8 个并发上传，但
  主机应用逻辑仍是单接收槽位。顺序队列让主机、查看器和校验保持一套状态机，
  也避免多个上传同时抢视频/音频的发送预算。并发留到以后有明确需求时再加。
- **不传空目录。** 文件传输的单位仍是文件；空文件夹不会出现在主机上。
- **不跟随符号链接/目录联接。** 展开时跳过 reparse point，避免循环、越界
  读取和重复内容。
- **不做压缩、断点续传跨会话、文件夹选择器按钮。** 文件夹通过拖放进入队列；
  断点续传仍只在同一会话内、同一主机、同一 .part 上生效。
- **主机 → 查看器的下载仍是单文件。** 协议字段对两个方向通用，但本阶段只把
  查看器 → 主机做成队列；主机的下载入口保持现状。

关键语义：

1. **相对目录是建议，不是路径。** 主机只接受“相对接收目录”的目录部分，
   逐段消毒后创建；绝对路径、盘符、`..`、空段一律拒绝。文件名仍走原有的
   `sanitize_received_name` 与唯一名处理。
2. **同名合并、同名文件不覆盖。** 两次拖入同名文件夹会合并到同一个接收
   目录（目录已存在就复用），但叶子文件重名时沿用 `name (1).ext`。
3. **顺序队列，失败不阻塞后续。** 单个文件哈希失败、主机拒绝或摘要不符，
   只结束该文件；队列继续下一个。权限被撤销时整个队列一起停下。
4. **队列状态可解释。** 查看器状态多一个 `file_queue`（尚未结束的条目数）
   和当前条目的相对目录；发送中的覆盖层显示“当前文件 + 队列剩余”。

## 2. 协议 v22

版本从 21 升到 22，ALPN 保持 `chast/1`。不新增控制消息类型，只扩展
`FileOffer = 21` 的载荷：

```
u32 transfer_id
u64 size
u8  flags                  // bit0 = resume
u8  sha256[32]
u16 name_len
u8  name[name_len]
u16 relative_len           // v22 新增；0 表示接收根目录
u8  relative[relative_len]
```

`relative` 是 UTF-8、以 `/` 分隔的目录相对路径（不含文件名），例如
`Trip/2024`。约束：

| 项 | 限制 |
| --- | --- |
| 编码 | 合法 UTF-8 |
| 长度 | ≤ 1024 B |
| 层级 | ≤ 32 段 |
| 分隔符 | 只允许 `/`；禁止 `\` |
| 段 | 不能为空，不能是 `.` 或 `..` |
| 绝对路径 | 禁止前导 `/`、盘符（`X:`）和任何 `:` |

解析器仍接受没有 `relative_len` 的旧载荷（防御性兼容），此时按根目录处理；
线上版本号必须一致，实际连接不会混用格式。

## 3. 主机落盘

`FileReceiveOptions` 增加 `relative_path`，`FileReceiver::create()`：

1. 解析并消毒相对目录（`sanitize_received_directory`）：逐段复用文件名的
   非法字符替换、保留名转义和长度规则；`..` 等结构问题直接拒绝。
2. 从接收根目录开始逐段创建：已存在的段必须是普通目录且不是 reparse
   point；不存在的段用 `CreateDirectoryW` 建立，建完再确认属性。
3. 最后一级目录作为 `impl.directory`，叶子文件继续走唯一名、`.part`、
   sidecar 和摘要校验；断点续传的查找位置随目录一起变化。
4. 任一环节失败都以 `Refused` 回答并带上原因，不创建半截目录以外的副作用
   （已创建的上级目录保留，便于下次合并）。

主机仍只有一个接收槽位：队列由查看器保证顺序；并发的额外 offer 会收到
`Busy`，与现在一致。文件完成回调 `file_received(final_path, bytes)` 不变，
路径自然带上子目录。

## 4. 查看器队列

`ViewerEngine::SendFile(path)` 改为 `SendFiles(paths)`：

- 平台线程只做参数收集与入队，立即返回；枚举目录和 SHA-256 都在一个
  常驻工作线程上完成，视频/输入线程不受影响。
- 工作线程先展开待处理根路径，再按入队顺序逐个哈希；哈希完成的条目在
  会话线程的 `drive_file_upload` 中依次 offer、发送、收尾。
- 展开规则：顶层目录名作为相对目录的第一段；嵌套目录用
  `generic_u8string()` 拼接；普通文件直接入队（相对目录为空）。符号链接、
  设备、不可读项跳过；一个文件夹没有任何可发送文件时记录一条失败。
- 每个条目带唯一 `transfer_id`；主机应答、CFIL 数据、结果都按 id 归属
  当前条目。单个条目失败只影响自己。
- 权限撤销：当前条目以 `Cancelled` 结束，队列其余条目清空并停止展开；
  会话结束同理。计数只把可见的失败算一次，避免一次撤销刷出一串弹窗。
- 队列上限 10000 个条目，超过的部分丢弃并在日志中说明。

状态新增：

| 字段 | 含义 |
| --- | --- |
| `file_relative_path` | 当前/最近条目的相对目录（根目录为空） |
| `file_queue` | 尚未结束的条目数（含正在发送的一个） |

`file_name`、`file_size`、`file_sent`、`file_error` 与计数器的含义保持不变；
队列清空后保留最近一次终态，供页面弹一次结果提示。

## 5. 查看器 UI 与 bridge

- `sendFile` 选择器改为多选，返回加入队列的文件数；取消返回 null。
- `sendFileAt` 接受 `List<String>`，一次拖放的多个条目全部入队；
  `WM_DROPFILES` 调 `DragQueryFileW` 逐个取路径后发 `droppedFiles`。
- Flutter 拖放回调改为文件列表；发送入口提示“已加入队列 N 个文件”。
- 发送进度覆盖层显示当前文件名（相对目录 + 叶子名）、阶段、字节数和
  “队列剩余 N 个”。单个文件时与旧版一致；接收下载覆盖层不变。
- 每个文件完成/失败仍用现有计数器触发一次 SnackBar，不额外做文件列表页。

- 发送中撤销文件传输权限：当前取消、队列清空、后续不再出现新 offer。
