# M6.0 — 弱网 QoS：帧率阶梯与音频预算

状态：已完成（2026-10-22）
上一阶段：M5.3 远端指针（原生光标）已完成。
下一阶段：文件传输、音频质量调优。

## 目标

M5.0 的自适应码率只有一个杠杆（CBR 目标码率），并且把配置码率整块
当成视频预算。这一步补两点：

1. **帧率阶梯**：码率降下去以后，帧率跟着降，保证低码率下每帧仍有
   足够比特（1080p、500 kbps、30 fps 只有 0.008 bpp，画面会糊成色块；
   同样 500 kbps 降到 10 fps 是 0.024 bpp）。帧率是低码率下的画质杠杆，
   不是省带宽的手段——CBR 下降低帧率不会减少发送字节。
   映射按“目标码率 / 上限码率”的比例分四档：≥70% 满帧率，
   45–70% 2/3，25–45% 1/2，<25% 1/3（不低于 10 fps，且不超过配置值）。
2. **音频预算**：音频是恒定的 ~160 kbps CBR，以前视频仍按整个配置码率
   发送，两者相加会超出运营者配的预算。现在视频上限 = 配置码率 −
   音频码率 − 10% 开销；音频未启用时全额留给视频。

两者都必须可重复验证：控制器是纯逻辑，测试直接喂合成样本；主机侧
用 `chast-quic verify` 的回环断言重公告里的帧率与码率一致。

## 非目标

- 分辨率自适应（编码器重建代价大，且缩放会破坏 1:1 像素映射）。
- 音频降档（Opus / 48→32 kbps）与音频参与丢包反馈：音频包已经是
  非阻塞发送，拥塞时先丢音频包，天然让位给视频。
- 真实弱网链路仿真（`tc netem` 等价物）：本轮用合成样本覆盖决策，
  真机弱网仍待两台机器验收。

## 架构

```
                 ┌──────────── BitrateController（纯逻辑） ────────────┐
  TransportStats → 丢包率 / RTT 膨胀 / 发送队列占拥塞窗口             │
                 │        │                                            │
                 │        ├─ 降：码率 ×0.7 / ×0.85（冷却 1.5 s）        │
                 │        │      帧率 = f(目标码率 / 上限)             │
                 │        └─ 升：每 3 s 健康 +100 kbps，回到上限为止   │
                 └───────────────┬────────────────────────────────────┘
                                 │ BitrateDecision{bitrate, framerate}
                                 ▼
                       HostServer::stream_session
                    ├─ set_rate(kbps, fps)（一次 reset，不重建会话）
                    ├─ force_keyframe（reset 丢参考帧）
                    ├─ frame_interval 重算（采集节奏立刻变）
                    └─ refresh_stream（查看者浮层显示新帧率）
```

## 决策

- **帧率是码率的函数**，不是独立状态机：不引入第二套冷却与恢复计时，
  队列/丢包缓解后码率回升，帧率自动跟随，不会出现“码率回来了帧率
  还在 10 fps”的悬挂状态。
- **一次 reset 同时改两个参数**：VPL 的 rate control 用
  `FrameRateExtN` 折算每帧预算，只改采集节奏不改编码器会让 CBR 目标
  失真；`set_bitrate` 因此升级为 `set_rate(bitrate, framerate)`。
- **音频预算在上限侧扣除**：扣在上限而不是目标上，恢复逻辑（回到
  ceiling）也自然停在“视频 + 音频 = 配置预算”。
- **帧率下限 10 fps**：再低操作反馈就不可用了；宁可继续降码率。

## 验证

- `chast-bitrate-test`：四档映射的边界、严重/中度拥塞下码率与帧率同步
  变化、恢复时码率先回满且帧率跟随、音频预留改变上限后目标随之下降、
  预留超过上限时夹到下限。
- `chast-quic verify`：回环保持干净链路，断言 `StreamInfo` 的
  `framerate` 与主机侧报告一致，且 `abr_changes == 0`（干净链路不动）。
- 回归：`ctest -C Release`、`flutter analyze`、`flutter test`。

实测（2026-10-22，单机，1920x1080）：

- `chast-bitrate-test` 82 项断言全过。
- `chast-quic verify` 74 项断言全过、151 个访问单元；`serve --audio` 启动
  日志 `video budget 2601 kbps after reserving audio out of 2777 kbps`，
  摘要 `target-bitrate=2601 kbps framerate=30 abr-changes=0`。
- `serve --framerate 15` + `connect`：接收端 76 帧/4.99 s、sender 报告
  `framerate=15`，证明配置帧率经阶梯原样下行（15 fps、预算 100% 时不降档）。
- `ctest -C Release` 8/8。

## 已知限制

- 帧率阶梯只在决策点更新，采集循环里已经排定的下一帧不受影响
  （最多一帧延迟）。
- 音频预算按 `AudioInfo::bitrate` 固定扣除，不跟踪编码器实际的瞬时码率。
- 双机弱网（丢包/抖动的真实链路）仍需人工验收；本轮是合成样本 + 回环。
