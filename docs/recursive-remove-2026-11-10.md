# 文件夹递归删除与确认

日期：2026-11-10。接续 [发射端模块对比](host-rustdesk-module-comparison-2026-11-08.md) 的 G18/C34 缺口；RustDesk 对照仍为本地固定提交 `7423dced37845c48093b6f71bd82e4a16cc8c79d`。本轮只做递归删除，不改变共享根、隐藏项、多根目录或压缩块传输。

## 用户行为

文件面板删除文件夹时不再要求先手动清空。单个文件夹的确认框明确提示“文件夹及其内容将被删除，此操作不可撤销”；文件仍使用普通删除。多选批量删除中，选中的文件夹逐项发送递归删除，文件发送普通删除，确认框在包含文件夹时使用对应警告。批量仍是一个请求对应一个回答的顺序队列，任一失败会停止后续项并在页脚汇总成功/失败数量。

主机收到递归删除后先完整枚举整棵树：只要发现 reparse point（符号链接、junction 等）或只读条目，就整体拒绝并且不删除任何内容。预检通过后才先删文件、再按从深到浅的顺序删除目录。文件数加目录数上限为 200000，与观看端递归下载的遍历上限一致。

这是**删除**操作，没有回收站和撤销。预检只能保证“因 reparse point/只读而拒绝”时树保持完整；预检之后若本地程序占用文件、权限在运行中变化或磁盘出错，已经删除的部分不会回滚，主机返回对应错误码和原因。

## 协议和主机

协议升级到 **v64**，两端必须同版本部署。`FileOperation` 新增 `RemoveTree = 3`；`path` 指向要删除的文件夹本身，`new_name` 必须为空。旧版本主机不认识该操作，会把 `FileOpRequest` 判为未知操作，因此不能只升级一端。

主机仍先把相对路径解析到共享接收目录内，拒绝绝对路径、`..`、跨 reparse point 的路径和受保留的 `.chast-partial`。递归删除只作用于接收目录之下，且不会跟随树内的 reparse point；这些规则与列表、下载、上传和单文件删除共用。

观看端仍通过同一个 `fileOperation` 桥接方法发送操作，原生引擎接受 `RemoveTree` 作为无附加名称的操作。主机端无需新增控制消息，`FileOpResult` 的 `Ok/Refused/NotFound/IoError` 语义不变。

## 验证

- 协议与文件传输定向测试通过：`chast-protocol-test` 覆盖 `RemoveTree` 往返和“未知操作在 `RemoveTree` 之后被拒绝”；`chast-file-transfer-test` 覆盖非空树删除、缺失路径、只读条目整体拒绝后再清除属性删除、纯文件目标拒绝、树内 reparse point 拒绝且链接目标保留。
- `flutter analyze` 无问题；文件面板 50 项测试通过，包含单文件夹发送 `removeTree`、批量中文件夹/文件分别发送 `removeTree`/`remove`、取消不发送以及主机拒绝原因的展示。
- Windows 观看端 Release 构建通过：`flutter build windows --release`，产物为 `app/build/windows/x64/runner/Release/chast_viewer.exe`。
- 真实 QUIC 回环 `quic_file_browse` 通过（32.94 秒）：观看端在共享子目录下新建父文件夹和子文件夹，重命名父文件夹，然后用 `RemoveTree` 删除非空父文件夹，并通过再次列表确认其消失。
- 完整 Release `ctest` 全量结果见下方“全量回归”一节。

## 边界

- 仅 Windows 主机；其他发射端平台未实现。
- 不支持经 reparse point 的删除，也不清除只读属性来“强行删除”；需要管理员或文件所有者先处理只读项。
- 预检与删除之间仍存在路径被本地进程替换的竞态；与现有单文件删除和路径解析边界相同，本轮没有引入基于句柄的目录枚举。
- 无删除进度、暂停、撤销或回收站；超大树的 200000 项上限会直接拒绝。
- G18 其余项（多共享根/盘符、可协商压缩）仍待开发；隐藏文件选项已由同日 v65 补齐，见 [隐藏文件浏览选项](hidden-files-2026-11-10.md)。
