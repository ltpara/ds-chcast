# M5.1 — 剪贴板文本双向同步

状态：已完成（2026-10-22）
上一阶段：M5.0 自适应码率与 RTT/端到端延迟已完成。
下一阶段：M5 其余体验扩展（音频、文件传输、分辨率/帧率自适应等）。

## 目标

M5 的第二小块，先打通最常用的文本剪贴板，范围限定为 `CF_UNICODETEXT`：

1. **协议 v9**：新增 `ClipboardUpdate` 控制消息（双向），长度上限 256 KiB，只接受合法、非空、无 NUL 的 UTF-8 文本；`HelloAck`/`StreamInfo` 增加“剪贴板可用”标志位。
2. **会话层**：`QuicSession` 允许两端发送与收取剪贴板更新；服务端闸门默认关闭，由 `HostServer` 按设置打开；队列有界，畸形消息按传输错误计数。
3. **主机**：Win32 `CF_UNICODETEXT` 读写后端（UTF-8 ↔ UTF-16、`OpenClipboard` 重试）；会话开始时只“记住”当前剪贴板而不回传，之后本机变化才发送；远端更新写入后同步记住，避免回声。
4. **查看器**：`ViewerEngine` 暴露发送/收取接口与状态；Windows bridge 增加 `sendClipboard`/`takeClipboard`；Flutter 会话页 500 ms 轮询本机与远端，连接后先记住初值、只同步变化，并抑制回声。
5. **设置与托盘**：`host.ini` 新增 `clipboard=0/1`（默认开），托盘增加“同步剪贴板”复选框与菜单项，服务主机自动继承。
6. **可重复验证**：协议单元测试、`chast-quic verify` 用内存假剪贴板断言双向各一次、无回声，且既有帧/输入/遥测断言保持通过。

## 非目标（留给后续）

- 图片、文件、HTML/RTF 等富剪贴板格式；只同步纯文本。
- 剪贴板历史、大小分片与压缩；超过上限的文本直接不同步。
- 增量/合并输入法组合串；只在轮询时看到稳定文本后同步。
- 音频、文件传输、弱网 QoS 与分辨率/帧率自适应。

## 架构

```
查看者 Flutter 会话页                        主机 HostServer
  ├─ 每 500 ms:
  │   ├─ takeClipboard() ──► 写入本机剪贴板 ─► _last = 文本
  │   └─ 读本机剪贴板 ──► 与 _last 不同才 sendClipboard(text)
  │            │
  │            ▼
  │      ViewerEngine ── ClipboardUpdate(seq,text) ──► QuicSession
  │                                                     │ 控制流（可靠有序）
  │      ViewerEngine ◄── ClipboardUpdate(seq,text) ────┤
  │            │                                        ▼
  │            └────────────────────────────── 主机 500 ms 轮询:
  │                                                ├─ 收远端 → 写剪贴板 → last=文本
  │                                                └─ 读本机 → 与 last 不同才发送
  └─ StatsOverlay: 剪贴板 开/关、发送/接收计数
```

关键决策：

- **控制流而不是额外流**：剪贴板消息很小且低频，复用已有的双向控制流即可；QUIC 的可靠有序保证文本不会被拆分或重排，`seq` 只用于诊断与测试计数。
- **两端都只同步“变化”**：会话建立时先读取并记住当前剪贴板作为基线，不上传历史内容（隐私）；之后轮询发现与基线不同才发送。写入远端文本后立即更新基线，因此不会把刚收到的文本再发回去。
- **闸门在服务端**：`HelloAck`/`StreamInfo` 的 bit1 告知查看器是否可用；`QuicServerConfig::allow_clipboard` 默认 `false`，`HostServer` 按设置打开。未打开时服务端直接丢弃客户端更新，也不发送本机文本。
- **协议边界做 UTF-8 校验**：拒绝空串、NUL、超长与非法 UTF-8（含过长编码、代理对、超出 U+10FFFF）。NUL 会让 `CF_UNICODETEXT` 截断，必须挡在协议层。
- **轮询而不是剪贴板监听链**：`AddClipboardFormatListener` 需要窗口与消息循环；主机已有托盘窗口但会话在 worker 线程，查看器在引擎线程。统一用 500 ms 轮询，逻辑简单且两端一致，代价是最多 500 ms 的同步延迟。
- **失败不阻塞视频**：剪贴板读写失败（被其他进程占用、非文本格式）只跳过本轮；远端消息畸形计入传输错误，不关闭会话。

## 协议 v9

控制消息：

- `ClipboardUpdate = 12`，载荷：`seq`（u64）+ UTF-8 文本（其余全部字节）。
- 文本长度 `1..kMaxClipboardBytes`（256 KiB），必须是合法 UTF-8、不含 `U+0000`；解析要求无尾随歧义（长度由控制头给定）且版本匹配。
- `HelloAck`/`StreamInfo` flags：bit0 = 输入可用，bit1 = 剪贴板可用（`kServerInfoClipboardEnabled = 0x0002`）。解析拒绝未知 flags 位。
- 两端都可发送；同一会话内 `seq` 从 1 递增，仅用于日志/断言，不做去重。

## 验证计划

1. **单元**
   - 协议：双向往返、最大长度、空/超长/NUL/非法 UTF-8 拒绝、HelloAck 标志位与未知位拒绝。
   - 会话：服务端闸门关闭时不上交更新且自己拒绝发送，开启时双向可达；队列有界；畸形消息计入传输错误。
   - 设置：`clipboard` 往返、默认值与非法值回退。
2. **构建**：Release 全量构建；`ctest -C Release` 全部通过；`go vet`/`go test`；`flutter analyze`/`flutter test`/`flutter build windows --release`。
3. **回环**：`chast-quic verify` 默认用内存假剪贴板覆盖该路径（无需额外开关）：
   - 主机发 1 条、收 1 条，查看器收 1 条、发 1 条；
   - 文本内容逐字相等；
   - 主机写入查看者文本后不再回发，查看器应用主机文本后不再回发（计数恰为 1 证明无回声）；
   - 另起一个关闭闸门的服务端，断言 HelloAck 报告关闭、服务端拒绝发送、查看者更新被丢弃；
   - 既有帧/CRC/解码/摘要/输入/RTT/帧龄/ABR 断言全部保持通过。
4. **UI 与真实剪贴板**：托盘复选框随设置持久化；会话浮层显示剪贴板状态与计数。用 `chast-quic serve --clipboard` 与 `connect --clipboard`（`--send-clipboard`）配合 `Set-Clipboard`/`Get-Clipboard` 实测真实 Win32 读写；单机环境不做人工鼠标操作验收。
5. **清理**：回环进程退出、端口释放、无多余注册或临时文件。

## 风险与边界

- **500 ms 轮询延迟**：快速连续复制会合并，只同步最后一次稳定文本；这是本块的已知体验取舍。
- **剪贴板被占用**：`OpenClipboard` 最多重试约 50 ms，失败则跳过本轮，下一轮再试。
- **大文本**：256 KiB 上限避免控制队列被单条消息长期占用；超大文本静默不同步（可由后续版本分片）。
- **防回声依赖基线**：如果本机在远端文本写入后、基线更新前发生并发复制，可能丢失一次同步；轮询间隔内概率很低，且不会形成回环。
- **隐私**：只同步会话建立后的变化，不上传连接前的剪贴板内容；闸门默认关闭，必须主机显式允许。
