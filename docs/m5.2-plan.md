# M5.2 — 系统声音单向传输

状态：已完成（2026-10-22）
上一阶段：M5.1 剪贴板文本双向同步已完成。
下一阶段：M5 其余体验扩展（文件传输、分辨率/帧率自适应、弱网 QoS）。

## 目标

M5 的第三小块：把主机正在播放的系统声音送到查看者，首版只做主机 → 查看者单向，不含麦克风。

1. **协议 v10**：`ServerInfo` 追加音频参数块并用 flags bit2 公告可用；新增 48 字节 `AudioHeader`、`AudioCodec` 与音频流解析器；流格式按版本严格校验。
2. **传输**：服务端在 `announce()` 时按闸门打开第二条单向 QUIC 流；音频包有独立序号、采集时间戳与 CRC32；视频流不受影响。查看者按包头 magic 区分两条流，不依赖流创建顺序。
3. **采集与编码**：WASAPI loopback（共享模式、事件驱动）采集系统混音，48 kHz 优先、实际按设备混音格式，立体声 s16；FFmpeg 原生 AAC-LC 编码（静态链接，不引入新运行时依赖），1024 样本/帧（48 kHz 下约 21.3 ms）。
4. **播放**：查看者 FFmpeg AAC 解码 → WASAPI 共享模式渲染；以主机 `capture_ms` 为时间线、结合 `LatencyReply` 学到的时钟偏移做排程，默认 80 ms 抖动缓冲；欠载时补静音、超时丢弃，缓冲深度与欠载次数进遥测。
5. **设置与 UI**：`host.ini` 新增 `audio=0/1`（默认开），托盘增加“共享系统声音”；查看者工具栏静音按钮，浮层显示音频编码/采样率/缓冲/收包计数。
6. **可重复验证**：协议/编解码单测；`chast-quic verify` 用合成正弦音源与测试接收端断言音频包数、CRC、解码样本数、能量与关闭闸门探针；真实 WASAPI 采集/播放另做单机回环。

## 非目标（留给后续）

- 麦克风上行、双向语音、回声消除。
- 设备热切换的双端点无缝交叉淡化：首版只做单端点跟随与原地恢复（见“Windows 音频健壮性”）。
- 多声道（>2）保真、空间音频、Opus/无损编码、码率自适应。
- 音频与视频的精确唇音同步校准（首版按同一主机时钟排程，误差在数十毫秒量级）。
- 文件传输、分辨率/帧率自适应。

## 架构

```
主机                                                 查看者
  WASAPI loopback（采集线程）
    └─ AAC-LC 编码（1024 样本/帧）
         └─ 有界队列 ── HostServer 主循环 drain ──► QuicSession::send_audio
                                                        │  第二条单向流
                                                        ▼
                                              QuicSession 音频队列
                                                        │  magic 分类
                                                        ▼
                                              AAC 解码 + 时间线排程
                                                        │
                                                        ▼
                                              WASAPI 渲染（抖动缓冲/静音）
```

关键决策：

- **独立单向流而不是塞进视频流**：视频访问单元可能有数 MB，混流会产生队头阻塞；独立流还能让音频在视频编码阻塞时继续到达。QUIC 的单向流天然只由主机发送，查看者无需开流。
- **流类型靠 magic 识别**：QUIC 不保证两条流的第一帧按创建顺序到达，因此不假设“第一条单向流是视频”。每条单向流的前 4 字节分别是 `CFRM`（视频）与 `CAUD`（音频），客户端在收到首个分片时分类；未知 magic 记为协议错误。
- **AAC-LC 而不是 Opus**：vcpkg 静态 FFmpeg 自带原生 AAC 编码器与解码器，零新增依赖；Opus 编码需要额外静态 libopus。AAC 的算法延迟约 25 ms，在 80 ms 抖动缓冲内可接受。后续若引入 libopus 再评估切换。
- **固定 48 kHz 立体声上行**：共享模式 loopback 拿到设备混音格式后统一重采样/下混到 48 kHz 立体声 s16 再编码。线上格式与设备解耦，默认输出变化不需要重新协商 `AudioInfo`，>2 声道也不会把声道布局不确定性带给查看者。
- **采集线程负责编码**：WASAPI 事件驱动线程按设备节奏取包、统一到 48 kHz 立体声、编码，再把压缩包投进有界队列；主机线程只在帧循环里 drain 并发送。这样音频节奏不被 30 fps 视频循环拉长，同时发送仍留在会话的单一线程上。
- **音频发送不阻塞视频**：`send_audio` 使用非阻塞发送路径；发送队列满时丢弃本音频包并计数。音频丢一包只会造成一次短暂杂音，阻塞视频则会让整幅画面卡住。
- **时间线排程**：音频包的 `pts_ms` 与 `capture_ms` 都取自主机 `steady_clock`，与视频帧、LatencyReply 同一时钟域。查看者把 PCM 按“主机时间 + 时钟偏移 + 目标提前量”排程，WASAPI 端点缓冲内的时长计入提前量；队列超前补静音、落后丢整帧。默认提前量 80 ms，兼顾网络抖动与唇音偏差。
- **失败降级不拖垮视频**：启动时打不开设备、或重采样/编码出现终端错误，只关闭音频：发送 `StreamInfo(audio.enabled=false)` 并优雅结束音频流，视频继续。运行中端点失效或默认输出变化属于可恢复事件，采集与播放在原地跟随新默认端点重连，不结束音频流；查看者协议错误的音频包只计数并丢弃，不结束会话。

## 协议 v10

版本号从 9 升到 10；ALPN 仍为 `chast/1`，版本不匹配在 Hello/控制头/帧头处明确报错。

`AudioHeader`（48 字节）：

| 偏移 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0 | magic | 4B | `CAUD` |
| 4 | version | u16 | 10 |
| 6 | flags | u16 | 保留，必须为 0 |
| 8 | seq | u64 | 音频包序号，从 0 递增 |
| 16 | pts_ms | u64 | 主机会话时间线上的呈现时间 |
| 24 | capture_ms | u64 | 主机 steady_clock 毫秒，取低 48 位 |
| 32 | payload_size | u32 | AAC 原始访问单元长度 |
| 36 | payload_crc32 | u32 | 载荷 CRC32 |
| 40 | sample_rate | u32 | 实际编码采样率 |
| 44 | frame_samples | u16 | 1024 |
| 46 | channels | u8 | 1 或 2 |
| 47 | codec | u8 | 1 = AAC-LC |

`ServerInfo` 保持既有字段与顺序，在显示器列表之后追加音频参数块：

- `u8 audio_enabled`、`u8 audio_codec`、`u16 channels`、`u16 frame_samples`、
  `u32 sample_rate`、`u32 bitrate`、`u16 extradata_size`、extradata 字节。
- extradata 是 AAC 的 AudioSpecificConfig（通常 2 字节），上限 64 字节；未启用时写默认值（48 kHz 立体声、1024、空 extradata）并由 flags bit2 表示关闭。
- flags：bit0 输入、bit1 剪贴板、bit2 音频；未知位仍拒绝。解析拒绝未知 codec、非法采样率/声道/帧长与超长 extradata。
- `HelloAck` 与 `StreamInfo` 逐字节相同；音频中途关闭走 `StreamInfo`。

## 采集、编码与播放

- **WASAPI loopback**：`IMMDeviceEnumerator` 取默认渲染端点，`IAudioClient` 共享模式 + `AUDCLNT_STREAMFLAGS_LOOPBACK | EVENTCALLBACK`；`IAudioCaptureClient::GetBuffer` 读取；`AUDCLNT_BUFFERFLAGS_SILENT` 时给重采样器喂零。设备失效后关闭端点，每秒重试并跟随新的默认输出，恢复后继续使用同一 `AudioInfo`。
- **格式**：接受 `WAVEFORMATEX` PCM 16-bit 与 IEEE float 32-bit（含 extensible 子格式）；float 限定到 [-1,1] 后转 s16；统一重采样/下混到 48 kHz 立体声 s16 再编码，设备侧 8–192 kHz、任意声道数都不改变线上格式。
- **AAC 编码**：FFmpeg `AV_CODEC_ID_AAC`，profile AAC-LC，`AV_CODEC_FLAG_GLOBAL_HEADER`，bitrate 160 kbps，frame_size 1024，输入 s16 交织经 libswresample 转 fltp；输出包忽略 FFmpeg pts，按“首块采集时刻 + 已编码样本数”生成主机时间线 pts。
- **AAC 解码**：用 AudioInfo.extradata 初始化；输出 fltp 经 libswresample 转 s16 交织；丢弃首帧的 1024 个 priming 样本。
- **抖动缓冲**：解码块进入按 pts 排序的队列；每次 WASAPI 事件按端点 padding + 80 ms 提前量取数据。到期数据不足补静音并计一次欠载；陈旧数据（落后超过一个帧长）整帧丢弃。队列上限约 500 ms，超出丢最旧。
- **静音**：桥接线程只更新原子标志；渲染线程在事件里以零块覆盖输出，并在端点支持时同步 `ISimpleAudioVolume::SetMute`，不中断解码与缓冲，取消静音后立即可听。

## Windows 音频健壮性（2026-10-22 补强）

- **固定上行格式**：采集端不再跟随设备混音格式，统一到 48 kHz 立体声 s16；设备采样率/声道数变化只重建端点与重采样器，不重新协商 `AudioInfo`。
- **静音门控**：连续数字静音达到 `silence_gate_ms`（默认 2000 ms，0 关闭）后停止向编码器喂样本，网络侧不再产生音频包；门控不改变时间线，恢复时由编码器按采集间隙重新锚定。loopback 在完全无声时不产包的设备本来就不占带宽，门控覆盖的是持续输出零缓冲的端点。
- **淡入**：采集恢复、门控退出或采集间隙超过 100 ms 时，对前 5 ms 应用线性淡入；播放器在启动、欠载恢复与端点重建后同样淡入，避免爆音。
- **设备跟随**：采集与播放各自每秒检查默认渲染端点 ID 与端点状态；默认设备变化或端点失效即关闭旧端点、原地重开新默认端点，失败则每秒重试。恢复期间查看者只听到短静音，音频流与会话不中断；启动时打不开端点仍是终端失败。
- **遥测**：`AudioCaptureStats` 增加 `gate_transitions`、`gated_frames`、`recoveries`、`recovering`；`AudioPlayerStats` 增加 `recoveries`、`recovering`；`HostServerStats` 镜像采集侧恢复与门控状态；`chast-quic` 打印 `gates`/`recoveries`/`recovering`；查看器状态与浮层显示播放端恢复次数与“设备恢复中”。

## 风险与边界

- **AAC 延迟与唇音同步**：编码+解码算法延迟约 40 ms，加上 80 ms 抖动缓冲，音频相对视频可能晚 50–100 ms；首版按同一时钟排程并记录缓冲，精调留待跨网阶段。
- **设备格式差异**：8–192 kHz、单声道/多声道、float32 都经 libswresample 统一到 48 kHz 立体声；设备拒绝打开仍会关闭音频并记录原因。
- **回环无真实网络**：抖动/欠载路径由时间线缓冲单测与人为延迟覆盖，真实弱网表现留待双机。
- **带宽**：160 kbps 约是 1080p 视频码率的 5%，ABR 目前只看视频发送；后续可让音频计入拥塞预算。
- **设备热切换**：采集与播放自动跟随默认输出并在原地恢复；切换瞬间会有短暂静音与欠载，不做双端点交叉淡化。单机回环无法在不改系统默认设备的情况下触发该路径，恢复逻辑目前只做了代码审查与正常路径回归。
- **静音门控**：部分驱动的 loopback 在完全无声时不产包，门控不会被触发，但此时本就没有音频流量；门控覆盖的是持续输出零缓冲的端点。门控期间查看者会补静音，恢复时可能计入欠载。
- **隐私**：默认开启系统声音共享，与剪贴板一致；不需要时可在托盘关闭，闸门在服务端。
