# G19 三项差异化能力决策（2026-11-14）

## 1. 结论

本轮完成 G19 的设计审查，但不直接进入编码。三项能力的目标设备、替代方案和
上线前置尚未同时满足；其中“查看端本地打印文件”不能替代远程打印语义，不能
用界面功能充数。当前决策如下：

| 能力 | 决策 | 原因 | 恢复条件 |
| --- | --- | --- | --- |
| 远程打印 | 暂缓 | Windows 任意应用要进入透明远程打印链路，仍需要一个可签名的虚拟打印队列；主机导出文件或查看端保存后打印都不是等价能力 | 获得可签名、可分发的 v4 打印机驱动，确定 Windows 版本与驱动部署/回滚矩阵 |
| Switch Sides | 不实施 | 当前查看器没有主机采集、编码、输入执行与服务端栈；反向交接需要合并两套进程模型或引入一次性凭据和本地 IPC | 主机与查看器合并为单一对等程序，并完成凭据不落盘设计 |
| AV1 4:4:4 | 暂缓 | 现有 AV1 是 Main Profile 的 4:2:0 硬件路径；4:4:4 需要 AV1 Profile 1、硬件编解码和目标 GPU 的全色度表面路径 | 明确支持的 GPU/驱动矩阵，且编码、传输、解码、渲染全链可保持零拷贝 |

G19 仍保持“设计完成、实现未获批准”，不把本文当作功能完成或兼容性声明。

## 2. 远程打印

### 2.1 目标语义

远程打印与“把文件下载到查看端”不同。目标语义是：主机上的应用照常选择打印机
并提交打印任务，任务在查看端选择的物理打印机输出；查看端不要求用户再次打开
应用、选择原文件或手工触发打印。

Windows 应用通常把页面提交给打印队列，而不是向远控进程直接提供可打印文档。
因此，要让任意 GDI/XPS/PrintTicket 应用透明进入该项目，需要一个虚拟打印队列
接收 spool 数据。这个队列需要打印驱动包及其渲染/端口适配组件。

### 2.2 候选方案

| 方案 | 能否实现透明远程打印 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| A. 自研或集成已签名 v4 虚拟打印机驱动 | 能 | 驱动签名、安装/升级/卸载、Spooler 权限、不同 Windows 版本、崩溃恢复和用户级杀毒兼容 | 唯一可达到 RustDesk 等价语义的方案；当前暂缓 |
| B. 调用系统“Microsoft Print to PDF”，监视输出目录 | 不能 | 用户必须主动选择 PDF 打印机和保存路径；不能可靠关联打印任务完成事件；同名/并发任务存在竞态 | 不采用为远程打印 |
| C. 主机应用导出文件，经文件传输到查看端后打印 | 不能 | 依赖应用是否支持导出，要求用户知道源文档；丢失应用自己的分页、打印机选择和宿主会话语义 | 只能作为“文件交付/查看端打开”功能，不能作为 G19 替代 |
| D. 截取窗口画面并按图像打印 | 不能 | 丢失分页、文本/矢量清晰度、多页和打印设置；可能截入遮挡窗口 | 不采用 |

### 2.3 后续实现门槛

若之后启动方案 A，至少需要以下设计与验收证据：

1. 确定支持范围，例如 Windows 10/11 x64 的企业部署；不支持的系统明确拒绝安装。
2. 驱动与配置安装必须经过签名验证，安装、升级失败和卸载均可回滚；不得把未签名
   驱动随便携包静默安装。
3. 打印队列与远控会话解耦：会话断开时任务失败可见，不得把主机 spool 数据写入
   查看端未授权目录或日志。
4. 定义最大任务大小、并发队列、超时、取消、同名任务和打印机离线处理。
5. 主机与查看端都记录可关联但不含文档内容的审计事件；日志不得保存正文。
6. 用真实 Word、Excel、PDF 阅读器、浏览器和文本编辑器覆盖分页、彩色、双面、
   纸张尺寸、多份打印和取消。
7. 在干净 Windows 虚拟机验证安装、升级、卸载、打印服务重启和异常退出恢复。

在这些条件满足前，不新增打印协议消息，也不把“查看端能打开 PDF”标记为远程打印。

## 3. Switch Sides

### 3.1 当前架构边界

chast 当前是不对称架构：主机负责采集、编码、输入注入和服务端接入，查看器负责
解码、渲染、输入发送和账号交互。查看器进程没有被授权的主机会话执行器，也没有
可直接复用的采集/编码服务。

### 3.2 可选路径

| 路径 | 影响 | 结论 |
| --- | --- | --- |
| 合并主机与查看器为一个对等可执行程序 | 需要统一生命周期、权限、采集、账户和更新模型 | 长期唯一干净方案，当前不做 |
| 查看端启动一个主机子进程并传一次性凭据 | 需要新增本地 IPC、凭据安全传递、进程完整性和双端授权 | 不符合当前“凭据不进命令行、不落盘”的约束，拒绝 |
| 反向 RDP 桥接 | 只覆盖启用了远程桌面的系统，接管本地会话，语义不等价 | 拒绝 |

### 3.3 恢复条件

只有在主机与查看器已经合并为单一对等程序，并能复用同一会话授权、设备身份和
更新/回滚机制时，才重新评估 Switch Sides。届时必须增加双机验收：反向方向切换、
一次性授权、拒绝/超时、切换中的媒体与输入释放，以及任一端崩溃后的恢复。

## 4. AV1 4:4:4

### 4.1 当前能力

项目已经支持 VP9 4:4:4，并通过现有的视频能力协商、GPU 解码和显示路径；AV1
编码属于硬件优先路径。当前 AV1 Profile Main 是 4:2:0，不能满足无损屏幕文字的
全色度目标。只把容器或能力字段改成 4:4:4 不会产生有效图像，反而会让接收端
按错误格式解码。

### 4.2 为什么暂缓

1. 需要目标 GPU 同时支持 AV1 Profile 1 的 4:4:4 编码与解码；仅有 AV1 Main
   硬件编码器不够。
2. 采集、色彩转换、编码表面、码流元数据和接收端纹理上传都需要全色度通道；
   任一环节降到 4:2:0 都会使该能力名不副实。
3. 项目约束要求硬件零拷贝，不能用 CPU 4:4:4 回退来制造测试通过但不可部署的路径。
4. 目前没有明确的商用 GPU/驱动最低版本和客户设备清单，无法定义稳定的回退策略。

### 4.3 恢复条件

启动前先确定目标设备矩阵和最低驱动版本，并完成以下设计：

- 协商字段明确区分 AV1 Main 4:2:0、AV1 Profile 1 4:4:4 和 VP9 4:4:4，不可只
  用“codec=AV1”推断色度。
- 编码器探测必须同时验证 profile、chroma、位深、分辨率、帧率和关键帧能力。
- 接收端在能力不匹配时拒绝该流并给出可诊断错误，不静默转 4:2:0。
- 测量编码/解码 GPU 占用、端到端延迟、文字清晰度与弱网码率；只有在至少两类
  目标 GPU 上通过后才进入产品默认路径。

在上述条件满足前，保持 VP9 4:4:4 作为全色度方案，AV1 仅用于现有硬件支持的
4:2:0 场景。

## 5. 当前交付与下一步

本轮交付是决策和验收门槛，不包含协议、驱动、客户端 UI 或媒体路径修改：

1. G19 三项不再作为“未决但不清楚边界”的工作悬挂；当前结论为远程打印暂缓、
   Switch Sides 不实施、AV1 4:4:4 暂缓。
2. 若产品决定投入远程打印，先准备签名、部署与回滚资源，再按 §2.3 立项；在资源
   到位前，优先完成已有的 ACL、双机传输和多屏/HDR 环境验收。
3. 若采购了明确的 AV1 4:4:4 目标硬件，再以真实编码器能力探测结果重开 §4；不以
   文档中的协议字段或软件编码测试替代硬件验收。
4. 本文不改变现有 VP9 4:4:4、文件传输、截图和查看端本地文件下载能力的状态。
