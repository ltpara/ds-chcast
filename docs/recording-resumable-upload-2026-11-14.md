# 录制归档断点续传（2026-11-14）

## 结论

查看器把会话录制上传到账号归档时，已从一次性流式请求改为持久化分片会话。
传输中断后，客户端查询服务端实际持久偏移并从该位置续传；服务端重启不会丢失
已确认的分片。旧 `POST /v1/account/recordings` 继续保留，供旧客户端和回退路径
使用。

本轮结果按证据层级分为：

- **已实现**：服务端分片会话、持久偏移、配额预占、完成校验、取消、Flutter
  自动续传、完成响应丢失核对和旧服务端回退。
- **自动化通过**：录制存储与 HTTP 专项、Go 全量测试/vet/build、Flutter 全量
  测试和静态分析。Flutter 首次全量回归发现 4 条新增错误文案缺少英文翻译，
  补齐后定向与全量测试均通过。
- **真实链路通过**：真实 `chast-server.exe`、临时 SQLite、真实文件；首片后强杀
  并重启进程，从持久偏移续传并完成，逐字节下载比对、SHA-256 和跨账号 404 均

- **生产未验收**：跨公网/NAT 长断线、生产反向代理请求体和超时限制、生产磁盘

## API

所有路由都要求账号 Bearer token；未启用录制归档时返回 503。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `POST` | `/v1/account/recordings/uploads` | 创建上传会话 |
| `GET` | `/v1/account/recordings/uploads/{id}` | 查询声明大小和持久偏移 |
| `PATCH` | `/v1/account/recordings/uploads/{id}` | 从指定偏移追加一个分片 |
| `POST` | `/v1/account/recordings/uploads/{id}/complete` | 校验完整文件并发布录制 |
| `DELETE` | `/v1/account/recordings/uploads/{id}` | 丢弃未完成会话 |

开始请求为严格 JSON：

```json
{
  "name": "session.mp4",
  "peer_id": "devbox",
  "size": 15728640,
  "started_at_ms": 1763100000000,
  "duration_ms": 9500
}
```

成功返回 201 和 `upload` 对象，包含 `id`、`offset`、`size`、`name`、
`peer_id`、`started_at_ms`、`duration_ms`、`created_at_ms`。`offset` 是服务端
已经持久接受的字节数，不是客户端本地已读取或已发送的字节数。

PATCH 必须同时满足：

- `X-Upload-Offset` 等于服务端当前持久偏移。
- `Content-Length` 为 1 B–32 MiB。
- 分片结束位置不超过开始时声明的总大小。
- 请求体恰好包含声明的字节数。

匹配时返回 202 和新偏移；偏移过期或超前返回 409，响应中的 `offset` 是服务端
当前值，客户端据此恢复。分片为空、超过上限或越过总大小返回 400/413；未知或
属于其他账号的上传统一返回 404，不泄露会话是否存在。

完成请求只接受已经达到声明长度的会话。服务端从正式分片重新计算 SHA-256，
发布录制并返回 201、录制记录、账号用量和配额。未完成返回 400。完成后活动会话
文件被移除，再查询会话返回 404；已经发布的是独立录制记录，不会被后续取消会话
删除。

## 服务端存储与一致性

每个账号目录保存一个会话状态 JSON 和一个 `.part` 分片：

```text
<recordings-dir>/<user-id>/tmp-session-<upload-id>.json
<recordings-dir>/<user-id>/tmp-session-<upload-id>.part
```

上传 ID 为 128 位随机十六进制值并通过固定格式校验。状态文件用同目录临时文件、
`fsync` 和原子 rename 写入；`.part` 每片写入后执行 `fsync`。查询偏移直接读取
`.part` 的文件大小，因此“PATCH 已成功写入但响应丢失”和“服务端进程重启”都可
按同一机制恢复，不需要单独提交内存计数。

追加失败时采用可重试语义：短读、超写、`fsync` 失败或关闭失败都会把 `.part`
截断回请求开始前的偏移；只有完整写入并同步成功的分片才作为新偏移返回。Windows
实测表明不能依赖 `O_APPEND` 截断已追加内容，因此实现使用普通写句柄、显式
`Seek(offset)` 和 `Truncate(offset)`。

完成顺序为：

1. 确认 `.part` 大小等于声明大小。
2. 流式重算 SHA-256。
3. 在同一账号目录把 `.part` rename 为正式 `.mp4`。
4. 在同一数据库事务中复核账号配额并插入录制元数据。
5. 删除活动会话状态文件。

数据库插入失败时尝试把正式文件 rename 回 `.part`；恢复失败会记录日志，并由
后续 orphan 清理处理无法归属的文件。数据库约束是配额最终裁决，开始阶段的预占
不能让并发的完成请求突破配额。

配额预占以活动会话声明总大小计算。开始上传时同时检查单文件上限和
`已用 + 所有活动会话声明大小 + 新文件大小`；每账号最多 8 个活动会话。预占是
保守的：即使一个会话尚未发送字节，也按完整声明大小占用账号配额。删除或完成
会话后释放预占。该设计防止多个并发大文件先在磁盘上写满、最后才由数据库拒绝。

存储锁是单进程内的 64 路分片互斥锁，开始会话另有进程内互斥，保证本进程不会
因并发开始或并发完成绕过预占。它不提供跨主机或跨进程租约；两个服务进程不能
安全地同时写同一个 `--recordings-dir`。

## 客户端行为

`ServerApi.uploadRecording` 默认使用新会话接口：

1. 读取本地文件长度，发送开始请求。
2. 默认按 8 MiB 分片 PATCH，服务端单请求限制仍为 32 MiB。
3. 请求超时、连接失败或 409 后调用状态接口，以服务端持久偏移为唯一下一位置。
4. 同一分片连续中断最多恢复 4 次，之后给用户明确的可重试错误。
5. 完成后如果响应丢失，刷新录制列表，按名称、大小、对端、开始时间、时长和
   新近创建时间寻找已经发布的同一录制，避免重复上传。
6. 终端失败后 best-effort DELETE 活动会话；取消失败不覆盖原始失败。
7. 开始请求返回 404/405 时，自动回退旧单次 `POST /v1/account/recordings`。

新增的“上传多次中断”“上传已失效”“进度已变化”“同时上传过多”错误提示均
有中英文文案。

## 清理与恢复边界

现有 orphan 清理阈值是 24 小时。账号目录中 `tmp-` 前缀的分片、状态和临时文件
只有超过该阈值才删除。因此续传是长期可恢复的，但不是永久保留：连续 24 小时
没有文件写入的未完成会话可能在下一次清理轮次消失，客户端随后会收到 404 并
重新开始。活跃写入会更新 `.part` 的修改时间，不会因会话创建较早被误删。

清理轮次与上传请求之间没有跨进程租约。单进程中的条款依赖锁和原子文件操作；
多进程共享目录、网络文件系统的 rename/锁语义以及清理与写入的竞争均不在当前
支持范围内。
