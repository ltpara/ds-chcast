# M5.0 — 自适应码率与 RTT/端到端延迟

状态：已完成（2026-10-22）
上一阶段：M3.2b Windows 服务主机已完成。
下一阶段：M5 其余体验扩展（剪贴板、音频、文件传输等）。

## 目标

M5 的第一小块，先把“看得见的链路质量”和“能自动让步的码率”打通：

1. **协议 v8**：`FrameHeader` 携带采集时刻 `capture_ms`（复用原 7 字节保留区，头仍是 48 字节）；新增 `LatencyProbe` / `LatencyReply` 控制消息。
2. **会话层**：客户端周期性发送探针，主机在同一控制流上自动应答；客户端据此计算 RTT 与两端时钟偏移。新增 MsQuic `QUIC_STATISTICS_V2` 读取接口（RTT、丢包、拥塞窗口、发送字节、队列字节）。
3. **自适应码率（ABR）**：主机按 RTT 膨胀、丢包率、发送队列/拥塞窗口压力调节 oneVPL 编码目标码率；用户配置的码率为上限，调节后强制 IDR 并重公告 `StreamInfo.bitrate`。
4. **遥测展示**：查看者浮层显示 RTT、端到端帧龄和目标码率；主机托盘显示当前自适应码率与 RTT。
5. **可重复验证**：协议/控制器单元测试、`chast-quic verify` 回环断言（探针有应答、RTT 合理、帧龄合理、ABR 遥测可用）。

## 非目标（留给后续）

- 分辨率/帧率自适应：本块只调码率，不改采集与编码尺寸。
- 前向纠错、视频 datagram、QUIC 多路径：继续走可靠有序流。
- 真实弱网/跨网演练：本机只有一张网卡，ABR 的降码率路径由纯逻辑测试覆盖；跨网与限速器验证留到后续手工/双机阶段。
- 新增托盘设置项：ABR 默认开启，配置码率即上限；暂不做开关 UI。
- 音频、剪贴板、文件传输。

## 架构

```
查看者 (ViewerEngine / chast-quic connect)
  ├─ 每 1 s: LatencyProbe(t0) ──────────────┐
  │                                          ▼
  │                                    主机 QuicSession
  │  LatencyReply(t0,t1,t2) ◄────────── 自动应答（t1=收到，t2=发出）
  │  RTT = (t3-t0) - (t2-t1)
  │  offset = ((t1-t0) + (t2-t3)) / 2      // host_clock - client_clock
  │  帧龄 = (client_now + offset) - capture_ms*1000
  │
  └─ 显示：RTT / 端到端延迟 / 目标码率

主机 (HostServer)
  ├─ 捕获后记录 steady_clock 毫秒 → FrameHeader.capture_ms（48 bit）
  ├─ 每秒读取 TransportStats(V2)
  ├─ BitrateController.update(RTT, minRTT, 队列, cwnd, 丢包增量)
  │     └─ 变化 ≥1 档 → encoder->set_bitrate(target) + 强制 IDR
  │                     + StreamInfo(bitrate=target)
  └─ HostServerStats: target_bitrate / rtt_ms / abr_changes / send_kbps
```

关键决策：

- **同一时钟域**：`capture_ms` 与探针里的 `host_recv_us` / `host_send_us` 都取 `steady_clock` 自纪元起的读数。Windows 上即 QPC，同机一致；跨机由客户端拟合的 offset 校正，不依赖墙钟。
- **探针在控制流上自动应答**：主机在 MsQuic 回调里用非阻塞发送路径回包，队列满时丢弃本次探针而不是阻塞传输线程；客户端每秒重发，丢一两个样本不影响趋势。
- **ABR 是纯逻辑**：`BitrateController` 不依赖 Win32/GPU/网络，输入为累计计数和间隔，输出目标码率与原因；主机只负责采样和应用。这样弱网策略可在单元测试里完整覆盖。
- **配置码率即上限**：初始目标 = 编码器实际码率（配置为 0 时是硬件默认值）；只会向下让路，网络恢复后逐步回到上限。
- **码率变化必须配套 IDR**：oneVPL `set_bitrate` 内部 `MFXVideoENCODE_Reset`，参考帧状态失效；主机置 `force_keyframe` 并重公告 `StreamInfo`，查看者按既有路径处理（码率变化不重建解码器）。
- **不做基于发送速率的下调**：屏幕内容天然 VBR，发送速率低于目标并不代表拥塞；只看 RTT 膨胀、丢包和发送队列压力。

## 协议 v8

`FrameHeader`（48 字节，字段顺序不变）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| magic/version/flags | 4+2+2 | 版本升到 8 |
| seq / pts_ms | u64 / u64 | 既有语义 |
| payload_size / crc32 | u32 / u32 | 既有语义 |
| width / height | u32 / u32 | 既有语义 |
| codec | u8 | 1=H.264, 2=HEVC |
| capture_ms | **48 bit** | 主机 steady_clock 毫秒，取低 48 位 |
| reserved | u8 | 仍为 0 |

控制消息：

- `LatencyProbe = 10`，载荷 8 字节：`client_us`（u64，客户端 steady_clock 微秒）。
- `LatencyReply = 11`，载荷 24 字节：`client_us`、`host_recv_us`、`host_send_us`（均 u64）。
- 解析要求长度精确匹配，版本不符或尾部多余字节一律拒绝。

## ABR 策略

采样周期 1 s，命令间隔：

| 条件 | 动作 |
| --- | --- |
| 丢包率 > 10%，或队列 > 100% cwnd | 目标 ×0.70（严重） |
| 丢包率 > 3%，或 RTT > max(1.5×minRTT, minRTT+25 ms)，或队列 > 65% cwnd | 目标 ×0.85（中等） |
| 连续健康 ≥3 s：丢包 <1%、RTT 未膨胀、队列 <50% cwnd | 目标 += max(100 kbps, 上限/50) |
| 目标达到上限 | 不再上调 |

- 下调冷却 1.5 s（按 1 s 采样即最快每 2 s 下调一次）；下调后 3 s 内不恢复。
- 目标夹在 `[floor, ceiling]`，`floor = min(ceiling, max(500 kbps, ceiling/10))`。
- 每档变化都记录原因（`loss` / `rtt` / `queue` / `recover` / `clamped`），供日志与统计。

   - 既有帧数、CRC、解码、摘要、输入、重公告断言全部保持通过。

5. **清理**：回环进程退出、端口释放、无多余注册或临时文件。

## 风险与边界

- **探针增加控制流负载**：1 Hz、单条 32 字节，可忽略；应答队列满时直接丢弃。
- **oneVPL Reset 成本**：ABR 最快约 2 s 一次；屏幕内容编码重置通常 <100 ms，配套 IDR 会带来一次码率尖峰。
- **同机回环看不到降码率**：无丢包/排队，控制器应稳定在上限；降档路径由单元测试保证，跨网实测属于后续验收。
- **帧龄含义**：查看者浮层显示“采集→收到”而非“采集→上屏”，解码/呈现的几毫秒不计入，避免把本地 GPU 抖动算进网络。
