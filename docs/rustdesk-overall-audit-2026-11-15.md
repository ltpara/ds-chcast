## 1. 审核结论

**当前版本尚未达到“功能和性能全面对齐 RustDesk”的验收条件。**

Windows 核心远控链路已经相当完整。发射端的视频采集、编码、自适应、输入、音频、文件、终端、端口转发、摄像头、录制、隐私和虚拟屏等主干能力基本具备；接收端也能完成日常 Windows 远控会话；服务器在账号、策略、审计、录制归档、独立中继、企业身份和管理 API 等方面已经明显超过本机 RustDesk OSS Server 1.1.17 的范围。

尚不能通过总体对齐验收，原因有四类：

1. 发射端仍缺远程打印、Switch Sides，便携特权辅助服务只有一次性提权交接而没有可复用的常驻服务，虚拟显示后端（仅 usbmmidd）和软件编解码覆盖（软件仅 VP9）也较窄。
2. 接收端缺多连接标签、任意视图缩放、光标倍率、触控板细项、SVG 剪贴板、共享地址簿密码等一组 RustDesk 已有的产品能力。
3. 当前产品只支持 Windows。`CMakeLists.txt:13-14` 明确限制为 MSVC 和 Windows DXGI；若“对齐 RustDesk”包含其跨平台范围，这是阻断性差距。
4. 性能只有 ds-chcast 自身的本机测试和基准，尚无同硬件、同网络、同画面、同编码参数下与 RustDesk 的双产品 A/B。2026-11-16 控制器修复后，现有弱网专项恢复固定峰值 ≤3000 ms、恢复后 ≤300 ms 的判据，连续五次峰值为 1040–1648 ms，结束帧龄为 11–19 ms。修复前 1.5–6.6 s 的宽预算结果仅作为历史定位记录；当前结果仍不能证明与 RustDesk 性能对齐。

结论按三块划分：

| 模块 | 当前判定 | 说明 |
|---|---|---|
| 发射端 | 部分对齐，Windows 核心链路接近 | 主链完整，少数 RustDesk 功能和跨平台能力缺失；控制器修复后现有弱网专项连续五轮满足固定 3000 ms 峰值门槛，仍缺 RustDesk 同条件 A/B |
| 接收端 | 部分对齐 | 会话主流程可用，产品交互、输入偏好、缩放和多会话能力仍有明显缺口 |
| 服务器端 | 对 RustDesk OSS 大部分对齐且部分领先；未完成生产验收 | 企业功能面较强，但控制面 HA、多实例协调和生产跨区域压测未证明；不能据此宣称对齐 RustDesk Server Pro |

## 2. 审核范围和判定方法

本次同时检查源码、自动化测试、已有验收文档和本机性能数据。状态含义如下：

- **已对齐**：源码路径存在，主要行为有自动化或实际链路证据，能力与 RustDesk 对照项基本等价。
- **部分对齐**：核心路径存在，但覆盖范围、交互、后端、稳定性或真实环境证据不足。
- **未对齐**：RustDesk 基线中存在，我方没有等价实现。
- **有意取舍**：已有明确产品决定不实现，不能在总体功能对齐统计中算作完成。
- **待真实环境验收**：代码和回环自动化存在，但没有双机、跨 NAT、真实代理/CDN、目标硬件或同条件 A/B 证据。

本机没有 RustDesk Server Pro 源码，因此服务器企业能力只能与 RustDesk OSS Server 1.1.17 做源码对照。涉及 Pro 的结论只列出我方已实现能力，不给出“完整对齐 Pro”的判断。

### 3.3 发射端性能判断

已有代码具备接近成熟远控产品的视频性能机制：GPU 采集和编码、每订阅者有界队列、帧龄淘汰、反馈驱动 QoS、IDR 合并和退避。架构上已经不是“能传画面”的初级实现。

弱网专项条件为 3 Mbps 初始视频、1 Mbps 瓶颈、约 160 ms RTT、双向 3% 丢包（`tools/quic.cc:11291-11306`）。修复前在本机重跑 6 次，最大帧龄为 **1823 / 2346 / 2487 / 2965 / 3174 / 3540 ms**，固定 3000 ms 门槛下 2 次失败。逐帧日志显示峰值对应降档窗口内一次 1.8–2.8 s 的完整停顿：控制器等应用回执积压超过 2 s 才紧急降档，并收敛到 1 Mbps 瓶颈本身，没有给 IDR、重传和控制流留余量。

2026-11-15 曾把判据放宽为包含整个劣化窗口的 11–12 秒动态预算；该做法只能证明最终恢复，不能验收交互延迟。2026-11-16 已修复控制器：应用回执积压达到 500 ms 即紧急降档，持续积压按 500 ms 分桶继续收紧，紧急目标约 800 kbps。验收恢复固定峰值 ≤3000 ms、恢复后 ≤300 ms。连续 5 次真实回环峰值为 **1064 / 1648 / 1516 / 1040 / 1072 ms**，结束帧龄 11–19 ms，全部通过；`--netem-rate-kbps 0` 实跑峰值 1239 ms，也通过且不再除零。

因此发射端弱网能力判为：**当前内部 3 秒峰值门槛已稳定通过，修复前 1.5–6.6 秒积压问题已关闭**。与 RustDesk 的相对性能仍需同机 A/B 才能下结论，尤其是端到端输入延迟、玻璃到玻璃延迟、帧龄 P50/P95/P99、恢复时间、有效帧率和 CPU/GPU 占用。

### 4.3 接收端性能判断

查看端使用原生解码和 GPU 显示路径，自动化覆盖实际编码、QUIC、解码和渲染相关链路。现有证据主要证明功能正确性与单机回环稳定性，没有形成以下 RustDesk 同条件对照：

- 解码和渲染端到端延迟；
- 1080p、2K、4K，不同刷新率和多屏下的 CPU/GPU/显存占用；
- 窗口缩放、遮挡、最小化和 HDR 下的帧率稳定性；
- 双窗口、多会话和长时间运行的资源增长；
- 输入事件到远端呈现的 P95/P99 延迟。

接收端性能因此判为：**技术路径合理，本机回归较强，尚未证明与 RustDesk 性能对齐**。

`quic_weak_network` 原门槛是固定的 `max_frame_age_ms < 3000`。本轮在本机重测 6 次：

| 最大帧龄 | 旧门槛判定 |
|---:|---|

6 次里 2 次失败、4 次通过；失败与通过的运行都满足视频完整性、解码恢复和队列排空，
ABR 也都从 3000 kbps 降到 1000 kbps 后回升，差别只在降级窗口内峰值帧龄。

逐帧日志把差别定位到结构原因：所有 3 s 以上的峰值都出现在降档窗口内一段
1.8–2.8 s 的完整停顿里（例如一次运行 t=5.3–8.1 s 之间没有任何一帧送达），
对应一个新 IDR 在 1000 kbps 瓶颈上排队。查看器实测最大关键帧为 165–261 KiB，
即单是这一帧的传输就要 1.3–2.1 s；而按设计，ABR 在这条用例上不降分辨率
（`sent.resolution_changes == 0`），所以峰值帧龄有一个与几何相关的物理下限，
固定 3000 ms 常数无法同时适配 1080p 与 1440p。会话结束帧龄在这 6 次中始终正常。

第一版修正把判据换成“2 × 关键帧传输 + 2 × 单程延迟 + 500 ms 排队上限”，
但连续 4 次仍失败（4108 / 5944 / 5991 / 6846 ms，预算 3055–4858 ms）。两个对照
排除了丢包重传：`--netem-loss-percent 0` 得 2460 ms（预算 2682 ms），
`--netem-rate-kbps 3000` 得 2163 ms（预算 1593 ms），都不通过。把中继排队上限
临时改为 3000 ms 后 `qdrop` 归零、峰值降到 1718–1972 ms（3/3 通过），机制由此
定位：控制器收敛到瓶颈码率本身，链路没有余量；中继 500 ms 排队上限在 1 Mbps
下只容得下 62.5 kB，小于一个 1440p IDR（150–260 KiB），被排满丢弃的字节
要在可靠流上重传，其后的帧全部等待，所以劣化窗口是主项。

恢复 500 ms 队列后，判据改为 `劣化窗口 + 2 × 关键帧传输 + 2 × 单程延迟 + 500 ms`，
并保留“链路恢复后帧龄 ≤ 300 ms”的断言，连续 11 次全部通过：

| 1916 ms | 11386 ms | 25 ms | 88 |

而 1610 ms 那次为 0），分布 1.5–6.6 s，因此单次通过只说明链路未失控，

## 7. 优先级建议

### P1：完成“性能对齐”的证据链

1. 保持弱网固定 3000 ms 门槛的连续回归，并补齐 P50/P95/P99 统计；当前 5 轮峰值 1.0–1.65 s 已关闭内部积压缺陷，但仍需与 RustDesk 做同条件对照。
2. 建立 ds-chcast 与 RustDesk 的同机双产品 A/B：同一采集内容、分辨率、刷新率、码率、编解码器、网络条件和测量工具。
3. 用双机和跨 NAT 环境复测直连、中继、TCP/WS 载体、IPv6、断线恢复和长时运行。
4. 如果目标包含 RustDesk 的整体平台范围，把 macOS/Linux/Android/iOS 的产品边界和路线列为 P1；如果目标明确只做 Windows，应在需求中写明该排除项。

### P2：补齐影响企业部署和关键连续性的差距

1. 服务器控制面 HA、健康检查、自动切换、滚动升级和灾难恢复演练。
2. 多实例限流共享，以及录制归档的共享存储/租约协调。
3. 便携特权辅助服务，保证未安装场景下 UAC、安全桌面和管理员会话的连续性。
4. 扩展虚拟显示后端和自定义分辨率能力。
5. 根据客户场景决定远程打印、Switch Sides、主机录制集中上传是否进入产品范围。
6. 为共享地址簿密码设计端到端加密、权限和审计模型后再实现。

### P3：补齐查看端产品体验

多连接标签页、任意缩放、光标倍率、触控板选项、剪贴板按键发送、SVG 剪贴板、可配置快捷键、保持唤醒、LAN 发现隐私开关、默认仅查看偏好和静默自动更新。

## 8. 最终验收门槛

只有同时满足以下条件，才建议把项目状态改为“已对齐 RustDesk”：

1. 产品明确对齐范围：Windows 专用还是 RustDesk 全平台，OSS 功能还是包含 Pro 企业能力。
2. 三端功能矩阵中的未对齐项已实现，或经产品负责人书面排除并提供等价工作流。
3. Windows 原生、Flutter、Go 全量自动化连续通过，环境跳过项在具备 Window Station 权限的机器补测。
4. 现有弱网专项持续满足固定峰值 ≤3000 ms、恢复后 ≤300 ms 的门槛；2026-11-16 修复后的五轮记录已通过，后续变更仍需回归。更广网络与分辨率场景在测试前独立约定判据，不以修复前包含整个劣化窗口的宽预算代替交互延迟验收。
5. 完成与 RustDesk 的同硬件 A/B，至少覆盖 1080p、2K/4K、静态办公、滚动文本、视频内容、多屏、弱网和中继。
6. 完成双机、跨 NAT、IPv6、生产代理/CDN、PostgreSQL、独立中继和故障切换验收。
7. 给出可复现的性能报告，至少包含延迟分位数、有效帧率、画质、码率、CPU/GPU/内存、服务器吞吐和并发容量。

当前最准确的发布表述是：**ds-chcast 已形成较完整的 Windows 远控产品，核心链路与 RustDesk 接近，服务器能力相对 RustDesk OSS 较丰富；总体功能仍有明确缺口，性能对齐尚未通过同条件对照验收。**
