## 目的

M6.0/M6.1 的验证只有合成样本和干净回环：控制器逻辑正确，但
MsQuic 的拥塞控制、真实丢包重传、编码器重建与 ABR 决策从未在同一条
坏链路上一起跑过。本验收补上 `docs/m6.0-plan.md` 明确留空的
“`tc netem` 等价物”，用真实 UDP 数据报驱动整条链路。

## 工具

`chast-netem` 是查看者与主机之间的 UDP 透明中继：收包后按配置注入
单程时延、均匀抖动、Bernoulli 丢包和每方向带宽瓶颈（序列化 + 尾部
丢弃），再定时转发。QUIC 看到的就是一条真实坏路径，拥塞控制、丢包
检测和 ABR 的信号全部来自实际数据报，而不是合成样本。

选项与语义：

| 选项 | 含义 |
| --- | --- |
| `--delay-ms` / `--jitter-ms` | 劣化窗口内每包单程时延 + 0..N ms 均匀抖动 |
| `--loss-percent` | 劣化窗口内每包独立丢弃概率 |
| `--rate-kbps` / `--queue-ms` | 每方向瓶颈速率；序列化积压超过 `queue-ms` 时尾部丢弃 |
| `--degrade-at` / `--recover-at` | 劣化窗口；窗口外链路完全干净 |
| `--seconds` | 中继自身运行时长 |

每个方向的计数器分开报告：`rx`（收到）、`fwd`（转发）、
`loss-dropped`（注入丢包）、`queue-dropped`（瓶颈尾丢）、
`max-queue`（观察到的最长排队）。`loss-dropped` 是注入，不是链路
故障；`queue-dropped` 才是瓶颈真的撑不住。

中继的收发 socket 使用 16 MiB 的 `SO_RCVBUF`/`SO_SNDBUF`。这不是
调优而是正确性要求：默认 64 KiB 接收缓冲装不下一次分辨率切换后的
两个 IDR 突发，会在中继里静默丢包，让 ABR 以为是链路丢包。详见
“验收中发现并修复的问题”。

## 方法

拓扑（单机，全部走 127.0.0.1）：

```
chast-quic connect --port 45434
        │  UDP
        ▼
chast-netem  --listen-port 45434 --forward-port 45433
        │  UDP
        ▼
chast-quic serve --port 45433 --bitrate 3000 ...
```

`serve` 的 `--seconds` 在第一个 viewer announce 之后开始计时；
`connect` 的 deadline 是 `--seconds + 20`，但会在服务端 FIN 时提前
结束；中继的 `--seconds` 要覆盖两者，所以取得最长。

### 用例 1：干净对照（25 s）

```
chast-netem --listen-port 45444 --forward-port 45443 --seconds 40
chast-quic serve --port 45443 --codec h264 --bitrate 3000 --seconds 25 \
    --token smoke --token-reuse
chast-quic connect --host 127.0.0.1 --port 45444 --insecure \
    --token smoke --seconds 28
```

### 用例 2：劣化 + 恢复（95 s）

劣化窗口：中继启动后 8–28 s（≈ 查看者建连后 7–27 s）。

```
chast-netem --listen-port 45434 --forward-port 45433 \
    --delay-ms 80 --jitter-ms 20 --loss-percent 3 --rate-kbps 1000 \
    --degrade-at 8 --recover-at 28 --seconds 130
chast-quic serve --port 45433 --codec h264 --bitrate 3000 --seconds 95 \
    --token smoke --token-reuse
chast-quic connect --host 127.0.0.1 --port 45434 --insecure \
    --token smoke --seconds 98
```

两个方向同时施加：基准 RTT ≈ 160 ms，每方向 3% 丢包，每方向
1000 kbps，排队上限 500 ms。采集为 1920×1080，编码 VDENC AVC，
上限 3000 kbps / 30 fps。

诊断输出：

- 主机 ABR 日志现在带决策原因、RTT、本采样间隔的丢包增量、发送在途
  字节与拥塞窗口，例如
  `adaptive bitrate: loss; target 1785 kbps at 20 fps, RTT 635 ms,
  loss 49/122 pkts, queued 341540 of cwnd 109876`；
- 查看者打印超过 1000 ms 的帧龄警告；
- 查看者摘要打印 `frame-age`（结束时）与 `max-frame-age`（全程）。

## 验收中发现并修复的问题

第一版中继没有显式设置 socket 缓冲，Windows 默认约 64 KiB。分辨率
每次升档会连发两个 IDR，瞬时几百 KB；中继的接收缓冲溢出后静默丢包，
MsQuic 在一条本已干净的链路上报告丢包（例如 12/180、19/159），ABR
把目标从 1100 打回 935 kbps，分辨率随后退回 50%，形成“升档→丢包→
降档”的极限环。现象与真实拥塞无法区分，会把工具缺陷误判成链路问题。

把中继的 `SO_RCVBUF`/`SO_SNDBUF` 提到 16 MiB 后，同一 profile 在每次
升档后都是 `loss 0/103`、`0/88`、`0/149`，分辨率一路回到 100%，
极限环消失。验收工具本身必须先证明它不丢包，这也是干净对照里
`0 loss / 0 queue` 的意义。

## 阶跃降容：一次性收敛（2026-10-27）

旧控制器在 3× 阶跃下降时每 1.5 s 只降 15–30%，从劣化开始到 500 kbps
约 10.4 s，这期间编码器持续按高于瓶颈的速率出帧，可靠有序流只能
排队，帧龄峰值 7954 ms。现改为“按实测交付速率一口气落位”，仍未
触及协议：

- 采样从 1 s 提到 500 ms。发现窗口是帧龄的第一决定项：阶跃后
  0.5–1 s 内仍会按旧速率交出约 200 KB，这一部分无法追回。
- 控制器用两次采样的传输发送字节差（`BitrateSample::sent_bytes`，
  MsQuic 的累计发送字节）算线速率，再按本区间丢包比例折算：
  交付速率 ≈ 线速率 × (1 − 丢包率)。阶跃后线速率仍接近 2–3 Mbps
  （被瓶颈丢弃的包和重传都计入发送量），不折算会把目标落在瓶颈
  之上，队列继续长 1–2 s——实测出现过一次，峰值 7.7 s。
- 目标取交付速率的 65%：既在瓶颈以下，又为已排队的帧留出排空余量。
- 这个落位信号要求同时满足两件事：交付速率跌破目标的 70%，且发送
  队列已涨过拥塞窗口的 65%。前一条排除了“只是 RTT 升高、交付正常”
  的纯时延事件（否则 65% 落位会把一次 15% 的时延反应放大成约 37%
  的降幅）；后一条排除了“桌面没动、发送量本来就低”的内容事件——
  屏幕内容可变码率，空闲桌面在健康链路上也会远低于目标速率。
- 交付速率骤降且队列积压时不受下降冷却限制。冷却是为了过滤单个噪声
  样本，不是让已知的容量阶跃再等一个 1.5 s 周期。其余行为不变：
  -15%/-30%、1.5 s/3 s 冷却、地板、天花板与恢复阶梯。

同一场景复测（2026-10-27，加门槛后四次）：

| 指标 | 2026-10-22 旧控制器 | 无落位门槛 | 加 70% 门槛（第 8/9 次） | 再加队列条件（第 11/12 次） |
| --- | --- | --- | --- | --- |
| 首次降档 | 2550 kbps | 1895 kbps | 2550 kbps | 2550 kbps |
| 首次降档→落到瓶颈以下 | 约 10.2 s | 1.6 s | 0.55 / 0.53 s | 0.50 / 0.54 s |
| 帧龄峰值 | 7954 ms | 3847 / 4079 ms | 2248 / 2142 ms | 3183 / 3287 ms |
| >1 s 的帧 | 278 / 1850（15%） | 86 / 154 | 75 / 76 | 94 / 137 |
| >3 s 的帧 | — | 35 / 31 | 0 / 0 | 4 / 6 |
| 主机在途峰值（落到地板时） | 549 KB | 191 KB | 191 / 156 KB | 117 / 158 KB |
| 完整性 | 1850/1850，0 错误 | 1731/1731，0 错误 | 1739 收 / 1714 解、1734 收 / 1712 解，0 错误 | 1745/1745、1746/1746，0 错误 |
| 恢复 | +100 kbps/3 s 到 2700 | 95 s 到 2600 | 95 s 到 2600 | 95 s 到 2700 |

加门槛前先跑了两轮（第 5/6 次），峰值 4079 ms 与 3847 ms，>1 s 的
帧 154 与 86，>3 s 的帧 31 与 35。两轮的首个决策都是 1850/1895 kbps，
而当时交付速率仍在 2.9 Mbps（目标的 97%）附近：65% 落位把一次 RTT
升高当成容量阶跃，一口气降了 38%。加上“交付跌破 70% 才落位”的
门槛后，首个决策回到 -15%（2550 kbps）；下一个 500 ms 采样看到
2/29、2/31 丢包，在途 196/160 KB 对 cwnd 81/88 KB，才落到 500 kbps
地板。两次复测的峰值因此降到 2.1–2.2 s，>3 s 的帧归零。

队列条件（第 10–12 次）：只看“交付跌破 70%”还有一处误判——空闲
桌面本来就可能远低于目标速率，屏幕内容的突发不能被当成容量阶跃。
落位因此要求发送队列同时涨过拥塞窗口。第 10 次把门槛设成“队列超过
100%（严重积压）”时，阶跃后 0.5 s 拥塞窗口仍有 225 KB、队列只有
245 KB，落位晚了一个采样（9.52 s，峰值 3899 ms），说明门槛比问题
更紧；改成 65% 后，第 11/12 次都在阶跃后的第一个 500 ms 采样落位
（0.50 / 0.54 s 到 500 kbps），而空闲队列（约 0）仍不触发。单测
分别覆盖了“交付骤降 + 队列积压”落位与“线速率低 + 队列空闲”只降
15% 两条路径。

四次加门槛复测的峰值落在 2.1–3.3 s，差异不来自控制器：落位时间稳定
在约 0.5 s，而阶跃瞬间拥塞窗口里已有 81–199 KB 待发数据，按 1 Mbps
折算就是 0.7–1.6 s；再叠加 0.5 s 发现窗口与降到 50% 时的双 IDR。
第 12 次劣化窗口内还有一次周期性 IDR（t≈17.8 s）把帧龄再抬到
2.2 s：CBR 下的关键帧突发本身就是时延来源，这已超出码率控制器的
作用范围。

（完整性一列的解码差：分辨率切换后接收端重建解码器，新流首个关键帧
之前的访问单元被跳过，不计入解码数，也不计为错误；CRC/解码/协议/
序号错误均为 0，接收端摘要与主机一致。）

调参过程也一并记录：先按线速率的 80% 落位、保留 1 s 采样时，两次
复测峰值为 4.7 s 与 7.9 s；把余量收到 65% 后仍有 4.3 s 与 7.7 s。
两次 7 s 以上的共同点是目标落在了瓶颈之上（1043/1281 kbps 对
1000 kbps），队列继续增长。加入丢包折算后，同样两次运行降到 4.1 s
与 3.8 s，且都在 0.5–1 s 内落到瓶颈以下。由此可见：线速率是发送量，
不是交付量；在瓶颈处丢包率就是两者的差。

### 仍然存在的时延

- 峰值从约 8 s 降到 2.1–3.3 s 是控制器能做的部分。剩余峰值由发现
  窗口、阶跃瞬间的拥塞窗口与已排队的帧决定：阶跃后 0.5 s 内仍按旧
  速率交出的数据，以及接收窗口里已经按序排好的库存，都只能按瓶颈
  速率播放完；CBR 下的关键帧突发也在这条队列里排队。
- 这部分数据已经交给 QUIC 的可靠有序流，不能像 UDP 那样丢弃；
  主机侧的在途计数只覆盖尚未交给传输层的字节，接收窗口里的库存
  同样按序播放。再往下压需要发送端时延预算（超预算跳帧/丢帧，
  恢复时强制 IDR），或者让视频走 DATAGRAM，两者都改变现有行为，
  不在本轮范围内。

最初的三个方向仍然成立，按代价从低到高：

1. **快速收敛**（已做，见上）：不动协议，收敛从 10.4 s 压到约 1 s、
   帧龄峰值从 7954 ms 降到 2.1–3.3 s；剩余时延受发现窗口、拥塞窗口
   与可靠流排队限制。
2. **发送端时延预算**：按采集时间戳限制在途时长，超预算就丢采集帧，
   恢复时强制 IDR。前提是允许跳帧并接受跳帧后的参考链断裂。
3. **视频走 QUIC DATAGRAM + 帧级容错**（帧内刷新/参考选择）：彻底
   摆脱可靠有序流的队头阻塞，但这是协议层改动，代价最大。

双机验收仍是下一道关口：真实无线/蜂窝的突发丢包与上下行不对称会
检验 65% 余量与丢包折算是否过于激进，跨机时钟偏差则直接影响帧龄
本身的读数。

## 自动化弱网回环（2026-10-30）

上面那套手工双进程流程已折进 `chast-quic verify --netem`（ctest
`quic_weak_network`，超时 180 s，实测约 28 s）。同一进程启动真实的
`HostServer`、真实查看器循环和一条进程内中继：中继监听 `--port`，
主机在 `--port + 1`，查看器经中继连接，所有数据报仍是真实 UDP。
劣化窗口锚定在会话首个数据报之后（`start_on_first_packet`），采集与
编码初始化再慢也不会吃掉前 4 s 的干净段。

固定 profile：单程 80 ms + 0..20 ms 抖动、3% 注入丢包、每方向
1000 kbps、500 ms 排队上限；会话第 4–12 s 劣化，其余时间干净；
配置 3000 kbps / 30 fps，运行 25 s。检查关闭输入、剪贴板、音频、
文件、摄像头等无关探针，失败只可能来自视频链路。

断言（全部通过才打印 PASSED）：

- 完整性：每一帧都到达并解码，关键帧数一致，0 CRC、0 解码错误、
  0 序号间隙、0 协议违规、主机 0 发送错误；
- ABR：至少一次决策；最低目标低于配置码率且不低于地板（500 kbps）；
  结束时目标高于最低值、低于配置码率（确有恢复，未弹回天花板）；
  分辨率阶梯至少动过一次；每次码率决策都重新公告流描述，查看器收到
  会话中的公告，且最后一次公告与主机运行值一致；
- 链路证据：中继确实施加了注入丢包且无 socket 错误，RTT 可采样，
  帧龄有界，发送流可离线重放且访问单元数与发送数一致。

2026-10-30 实测（VS 2026 Release，串行 ctest，28.16 s）：目标
3000 → 500 kbps（6 次决策），分辨率 100% → 50%，结束时 15 fps；
发送/接收/解码 355/355/355，4 个关键帧，最大帧龄 2.9 s；中继
host→viewer 2435 收 / 2283 转发 / 17 注入丢包 / 135 尾丢，
viewer→host 525 收 / 9 注入丢包，两个方向 0 发送错误。同批 18 项
`quic_*` 回环全部通过；含该用例的全量串行 ctest 37/37 通过
（570 s）。

这项检查守住控制器、编码器重建与公告链路的逻辑回归；真实无线突发
丢包、跨机时钟偏差与 Flutter 呈现仍需双机人工验收（见下节）。

## 音频弱网复核（2026-10-31）

同一中继也用于音频（`serve --audio` + `connect --audio --play`，主机回环
播放低音量 440 Hz 保持静音门开启）。对比三种排程策略：旧 80 ms lead、
首块到达锚定、最终起播聚合（6 块，见 `docs/m6.3-lipsync-plan.md`）。

轻档（20 ms + 5 ms 抖动 + 0.2% 丢包，不限速，32 s）：

| 策略 | 播出 | 欠载 | 丢块 | skew |
| --- | --- | --- | --- | --- |
| 旧 lead 80 | 31.2 s | 10 | 42 | +45.3 ms |
| 首块锚定 | 30.1 s | 1 | 83 | +365.0 ms |
| 起播聚合（两轮） | 31.8 s | 0 | 0 | +261.9/+274.3 ms |

视频验收档（80 ms + 20 ms 抖动 + 3% 丢包 + 1 Mbps，42 s）：

| 策略 | 播出 | 欠载 | 丢块 | skew |
| --- | --- | --- | --- | --- |
| 旧 lead 80 | 3.45 s | 48 | 1927 | −58.5 ms |
| 首块锚定 | 16.91 s | 130 | 1183 | −427.2 ms |
| 起播聚合 | 21.22 s | 5 | 878 | +331.5 ms |

- 两档都满足“音频弱网欠载/丢块不高于旧 80 ms lead 基线”，聚合的播出
  时长也最长。轻档起播积压约 370 ms（前 17 块在 9 ms 内成串到达），
  60 ms 校正上限只吃掉一部分，仍剩约 240–250 ms 延迟；加长聚合窗口
  按最快块锚定会过度前移（干净回环 246 丢块/25 欠载），未采用。
- 视频验收档暴露的是传输层问题，不是排程：20 ms 抖动被 QUIC 当成
  丢包与重排，ABR 降到 500 kbps/10 fps、RTT 235–404 ms；可靠有序的
  音频被视频数据与重传拖后 0.2–3 s，三种策略都大量丢块。上文“发送端
  时延预算 / DATAGRAM”的结论对音频同样适用：需要不可靠音频 + PLC 或
  独立/高优先级流，才能在该档保住连续播放。该专项已于同日以 v35
  DATAGRAM 音频落地，见下节。

## 音频 DATAGRAM 对比（2026-10-31，协议 v35）

上一节把视频验收档的音频问题定位到可靠流被拥塞与重传拖后。v35 改为
协商后把音频包放进 QUIC DATAGRAM（设计、回退与识别魔数见
`docs/status-2026-10-25.md` §6.6）。`verify --netem` 增加 `--audio`
开关，同一档位直接 A/B：

```
build\Release\chast-quic.exe verify --netem --audio --seconds 25
build\Release\chast-quic.exe verify --netem --audio --audio-stream --seconds 25
build\Release\chast-quic.exe verify --netem --audio --play --seconds 25
```

`--audio` 让主机产生低音量 440 Hz 测试音并保持静音门开启；`--play`
额外启动本机 WASAPI 播放并统计欠载、丢块、slack 与 A/V skew；
`--audio-stream` 关闭查看者的 DATAGRAM 能力位，强制走可靠流。

视频验收档（80 ms + 20 ms 抖动 + 3% 丢包 + 1 Mbps，25 s）的传输完整性：

| 传输 | 接收/发送 | 丢包 | 解码时长 |
| --- | --- | --- | --- |
| DATAGRAM | 1248/1251 | 0.24% | 24.95 s |
| 可靠流 | 1250/1250 | 0 | 24.99 s |

同一档带播放的对比（单次回环，受 CPU 负载与注入随机性影响）：

| 传输 | 接收/发送 | 丢包 | 解码时长 | 欠载 | 丢块 | slack 均值 | slack 最差 | av-skew |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| DATAGRAM | 1212/1249 | 2.96% | 24.23 s | 1 | 368 | −99.5 ms | −1026 ms | +30.2 ms |
| 可靠流 | 1250/1250 | 0 | 24.99 s | 1 | 407 | −882.4 ms | −5934 ms | +26.0 ms |

- 可靠流虽然零丢包，但音频包在拥塞窗口里排队，平均比排程晚 0.88 s、
  最差 5.9 s，端点缓冲反复被吃穿；DATAGRAM 不可重传，平均迟到压到
  约 0.1 s、最差 1.0 s，3% 丢包没有增加欠载（两者均为 1 次起播欠载）。
  av-skew 基本不变，因为它衡量锚点相对视频帧龄的偏移，不含拥塞排队；
  该档要改善的是“是否连续可听”，不是首块对齐。
- 断言口径：DATAGRAM 模式要求 HelloAck/StreamInfo 的协商标志存在、
  丢包 ≤10%、0 CRC/解码/协议错误、音频流 FIN 到达、解码时长不少于
  视频时长的 90%（且至少少 1 s 的余量）；可靠模式仍要求发送数等于
  接收数、0 序号间隙。单机回环另有 200/200 包的严格用例。
- 已知限制：DATAGRAM 尾部包可能随会话关闭丢失（回环用例允许 ≤2%）；
  本工具是独立同分布丢包，真实无线突发与双机可听内容仍需人工验收。
  丢包隐藏已由下节的 Opus PLC 补齐。

### 丢包隐藏（Opus PLC，2026-10-31）

v35 之后丢包不再重传，解码器补上 Opus 内建 PLC：序号前跳时最多补 5 帧
（100 ms），更长的断流保持静音；落后于最高序号的迟到包直接跳过，
不再倒放。CLI 与 GUI 查看器共用同一套序号逻辑，接收摘要新增
`concealed`，`verify --netem --audio` 断言它不超过缺口帧数。

同一视频验收档 25 s 的三次 DATAGRAM 运行与一次可靠流对照：

| 运行 | 接收/发送 | 丢包 | gaps | reordered | missing | concealed | 解码时长 | 欠载 | 丢块 | slack 均值 | av-skew |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 无播放 | 1245/1253 | 0.64% | 18 | 22 | 30 | 30 | 25.05 s | — | — | — | — |
| 播放 #1 | 1241/1252 | 0.88% | 19 | 28 | 39 | 39 | 25.03 s | 1 | 400 | −35.3 ms | +56.2 ms |
| 播放 #2 | 1237/1250 | 1.04% | 19 | 19 | 32 | 32 | 24.99 s | 2 | 403 | −47.2 ms | +41.5 ms |
| 可靠流 | 1250/1250 | 0 | 0 | 0 | 0 | 0 | 24.99 s | 1 | 406 | −1187.5 ms | +27.7 ms |

- 三次 DATAGRAM 的 CRC/解码/协议错误均为 0，每个前跳缺口都由
  `concealed` 补齐（缺口均 ≤5 帧）。`missing` 按序号前跳计，包含
  随后到达但已过槽位的重排包，所以大于真正丢包数（8–13）。
- 0 lead 的到达锚定下，隐藏帧的槽位往往在到达时已经过去，播放器按
  既有规则丢弃过期块；因此欠载/丢块与加 PLC 前同一量级（1 对 1–2、
  368–407 对 400–403），slack 均值仍明显优于可靠流的 −1.19 s。
  PLC 保证解码输出与计数连续，并在有排程余量（成串到达或引入 lead）
  时可听；音乐级连续仍需自适应抖动缓冲（见下节实验）或包级修复
  （见“包级冗余评估”，Opus FEC 与 1+1 复制不采用）。
- 单测 `chast-audio-codec-test` 覆盖隐藏块的格式、捕获时间、时间线
  槽位（与参考解码器直接解码丢失包一致）、非静音能量、后续解码与
  无历史时的拒绝；`ctest -R "^(protocol|audio|audio_dsp|quic_loopback|
  quic_weak_network)$"` 5/5 通过。

### 自适应抖动缓冲实验（2026-10-31）

```
build\Release\chast-quic.exe verify --netem --audio --play --adaptive-jitter --seconds 25
```

`--adaptive-jitter`（隐含 `--audio --play`）在 0 lead 到达锚定上启用
`JitterLeadController`：500 ms 窗口内至少 2 块迟到 20 ms 时抬升 lead
（缺口 + 10 ms，单窗 ≤40 ms，上限 120 ms），连续 2 个早期窗口后每窗
回收 20 ms；起播 1 s 内与停顿重锚后 0.5 s 内的窗口不改变 lead；lead
入队时逐块固定，抬升不影响已排队块。详细设计与断言见
`docs/status-2026-10-25.md` §6.8。

视频验收档 25 s（默认与自适应各 6–10 次采样的范围／中位数；空转列
为 2026-10-31 补指标后的复测；自适应行括号内为加起播宽限与 2 窗
回收后的三次采样）：

| 配置 | 播出帧 | 欠载 | 空转总时长 | 丢块 | slack 均值 | jit 终值 | av-skew |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 默认（0 lead） | 805–814k（复测 727–746k） | 1–2 | 7980–8000 ms | 374–406 | −97…−107 ms | 0 | +30…+37 ms |
| `--adaptive-jitter` | 835–946k（复测 869–904k；宽限后 817–912k） | 1–13（中位 11.5；宽限后 1–10） | 6160–6940 ms（宽限后 6020–8000 ms） | 260–365（宽限后 295–371） | −39…−59 ms | 0–20 ms（峰值 120） | +27…+52 ms |

- 播出帧中位数约 +10%（范围 +3…+17%），丢块中位数约 −24%
  （范围 −10…−36%）；每次运行在劣化窗口内抬升 3 次到 120 ms、
  恢复后回收 5–6 次。
- 空转总时长（`AudioPlayerStats::starved_ms`，相邻已写入块的调度
  静默累计）显示自适应把实际静默缩短 14–23%（8.0 s → 6.2–6.9 s），
  与丢块 × 20 ms 吻合；默认模式“只记 1–2 次欠载”确系计数盲区，
  不是连续性更好。宽限后的三次采样为 8.0/6.16/6.02 s（两次
  −23…−24%、一次持平），播出 817k/906k/912k 帧、丢块 371/302/295。
- 起播宽限（2026-10-31）：4 s 干净回环中自适应不再抬到 120 ms，
  三次均只抬到 40 ms（raises=1、decays=0），skew +84/+76/+91 ms，
  默认同构建 +33…+40 ms；25 s 干净链路 jit=20 ms、skew +60.7 ms，
  默认 +44.6 ms。残余 20–40 ms 来自发送端按视频帧泵送时同一串内的
  块间排程差，要消除应改播放排程而非控制器参数。
- 判定仍保持默认关闭：起播钉死已消除，弱网连续性维持原收益，但
  干净链路仍多 20–40 ms lead；转默认还差双机可听验收。
- 该档欠载都发生在 lead 到顶或爬升中、平均 slack 仍约 −50 ms 时；
  根因是 80 ms 时延阶跃让锚点过期，120 ms 上限不足以同时覆盖
  阶跃与端点缓冲。恢复后 jit 回落到 0–20 ms；常规链路的稳态没有
  额外时延，但起播瞬态可能短时升到 120 ms。

### 发送侧固定 lead 实验（2026-10-31）

```
build\Release\chast-quic.exe verify --netem --audio --play --audio-lead-ms 40 --seconds 25
```

`--audio-lead-ms N`（1–500 ms，隐含 `--audio --play` 与发送侧锚定）按
主机采集时间戳加 N ms 排程，时钟偏移来自 LatencyReply；
`--audio-capture-anchor` 等价于 N=40。可与 `--adaptive-jitter` 组合，
此时 N 是底、控制器最多再加 120 ms。视频验收档 25 s：默认空转 8.0 s /
skew +32.1 ms，自适应 6.5 s / +45.6 ms，固定 40/80/120/160 ms 为
8.3/6.7/4.0–4.4/3.2 s 与 +33/+74/+112/+154 ms；40 ms 底 + 自适应两次
为 6.39/4.03 s 与 +32.6/+33.9 ms。洁净（零损伤中继）默认 0 ms /
+34.9 ms，固定 40 ms 27 ms / +29.9 ms，固定 80 ms 7 ms / +69.3 ms，
40 ms 底 + 自适应两次 27 ms 与 +26.7/+26.2 ms（12/25 s）。组合模式
兼得洁净低 skew 与弱网连续性，是 GUI 默认的首选候选；默认仍为到达
锚定，待双机可听验收，详见 `docs/status-2026-10-25.md` §6.10。

### 包级冗余评估（2026-10-31，不采用）

为判断“丢包即 20 ms 缺口”能否用包级冗余补上，评估了两条路线，
详细记录见 `docs/status-2026-10-25.md` §6.9。

```
build\Release\chast-quic.exe verify --netem --audio --netem-loss-percent 8 --netem-jitter-ms 2 --netem-rate-kbps 0 --seconds 25
```

- Opus 带内 FEC 只覆盖 SILK/LPC；`FEC=1` 会把 CELT 音乐模式切成
  SILK，`FEC=2` 无冗余，故排除。
- 1+1 DATAGRAM 复制（同一包发两次、序号不变）干净回环收到 400/200、
  `reordered=200`、0 错误；但弱网 A/B 无稳定收益，默认档 missing
  51–52 对基线 40，8% 丢包档 33–42 对 37–39，只有纯丢包档 29 对 45
  略好。
- 根因是 MsQuic 把背靠背两份 DATAGRAM 合并进同一个 UDP 数据报：
  纯丢包档中继侧 host→viewer 只从 3006 增到 3170 个数据报（副本约
  1250 份，约 87% 被合并），副本与原包共享丢包；`host drops=0` 表明
  丢包在链路而非主机队列。特性已回退，默认保持单副本 + PLC。
- 新增诊断参数（仅用于验证，不改变默认档）：`--netem-delay-ms`、
  `--netem-jitter-ms`、`--netem-loss-percent`、`--netem-rate-kbps`
  （0 关闭限速）；任一覆盖时跳过 ABR 断言并打印
  `profile: custom --netem values; ABR assertions skipped`。弱网音频
  行同时打印 `host drops`。

## 单机验收覆盖不到的差异

- 真实无线/蜂窝链路的抖动分布、突发丢包和上下行不对称；本工具是
  独立同分布丢包 + 均匀抖动。
- NAT、防火墙、MTU/PMTU、ECN；本工具全程 IPv4 回环。
- 两台机器的时钟偏差：帧龄依赖 `capture_ms` 与接收端时间的对应，
  单机天然为 0；跨机时由 RTT 探测估计 offset，误差会直接进入帧龄。
- 发送端与接收端的 CPU/GPU 竞争；单机上采集、编码、解码共享资源，
  不能代表低端查看者。
- 真实 Flutter 查看器的呈现路径与垂直同步；本验收用 `chast-quic
  connect` 的计时器，只到解码为止。

## 结论

- **通过**：码率/帧率/分辨率三杠杆在真实 QUIC 链路上按设计联动；
  劣化——恢复全过程的档位单调、有滞回、无抖动；分辨率重建后所有
  访问单元可解码，完整性零错误；干净链路 ABR 不动。
- **已改善（2026-10-27）**：容量阶跃的收敛从约 10.4 s 压到约 1 s，
  帧龄峰值从 7954 ms 降到 2.1–3.3 s（四次复测），>1 s 的帧从 278
  降到 75–137，>3 s 的帧从 31–35 降到 0–6；加门槛后四次复测的
  峰值差异主要来自阶跃瞬间拥塞窗口的大小（81–199 KB），不是控制器。
- **仍保留**：1–3 s 的峰值时延，来自 0.5 s 的发现窗口、阶跃瞬间的
  在途数据与可靠有序流的既有排队；要压到 1 s 以内需发送端时延预算
  或 DATAGRAM（见上节）。
- **音频（2026-10-31）**：轻档与视频验收档的欠载/丢块均低于旧 80 ms
  lead 基线；协议 v35 的 QUIC DATAGRAM 音频进一步消除了视频验收档的
  拥塞拖尾（slack 均值 −99.5 ms 对 −882.4 ms，见“音频 DATAGRAM
  对比”），可靠流保留为回退。
- **包级冗余（2026-10-31 评估）**：Opus 带内 FEC 不适用于 CELT 音乐
  模式；1+1 DATAGRAM 复制被 MsQuic 合并进同一 UDP 数据报，弱网 A/B
  无稳定收益，已回退（见“包级冗余评估”）。默认保持单副本 + PLC，
  修复能力留待独立数据报延时副本或交织奇偶 FEC。
- **仍待做**：双机（最好含真实 Wi-Fi/蜂窝）验收，重点看上述时延、
  65% 余量与丢包折算在突发丢包下的表现、时钟偏差下的帧龄，以及
  Flutter 查看器内的实际观感；音频侧的自适应抖动缓冲已实验实现但
  默认关闭（见“自适应抖动缓冲实验”），双机可听验收仍待做。

## 双机弱网验收步骤（2026-11-11，待两台真机执行）

单机验收已完成；本节把“双机验收仍待做”落成可执行清单。两台机器
必须使用**同一提交构建的 Release 产物**，并在同一局域网（或同一
Wi-Fi/手机热点）内。

### 拓扑

```
B：查看者 + netem                                    A：主机
chast_viewer ──UDP──> chast-netem 127.0.0.1:45434 ──UDP──> chast-host <A-IP>:4433
```

- netem 是 UDP 透明中继，对两个方向施加相同的延迟/抖动/丢包/限速；
  `--bind` 用默认 `127.0.0.1`，只服务本机会话。
- 查看者看到的是普通 `host:port`，所以统计面板**不显示“路径”行**，
  “传输”显示 `UDP`。若显示 `TCP 回退` 或 `WebSocket 回退`，说明
  UDP 没走通（常见于 VPN/代理/防火墙），本轮无效。
- 主机侧看到的源地址是 netem 的上游套接字，不是查看者本身；这是
  透明中继的预期行为。

### 前置条件

| 项 | 主机 A | 查看者 B |

### 步骤

1. A 启动主机。确认托盘提示监听 4433。
2. **干净对照**（证明中继本身不丢包）：B 启动
   `chast-netem.exe --listen-port 45434 --forward-host <A-IP> --forward-port 4433 --seconds 40`，
   查看者连接后保持 30 s；netem 汇总两方向 `loss-dropped=0`、
   `queue-dropped=0`，RTT <30 ms。然后断开查看者、结束中继。
3. B 启动 netem：干净 0–30 s，劣化 30–90 s，恢复 90–140 s。

```
build\Release\chast-netem.exe --listen-port 45434 --forward-host <A-IP> ^
    --forward-port 4433 --delay-ms 80 --jitter-ms 20 --loss-percent 3 ^
    --rate-kbps 1000 --queue-ms 500 --degrade-at 30 --recover-at 90 ^
    --seconds 140 --seed 1
```

4. netem 启动后 2–5 s 内，B 打开查看器，直连 `127.0.0.1:45434`，
   输入测试密码（“两者”模式下在 A 上点“允许”）；打开统计面板
   （工具栏“显示或隐藏统计”）。确认：`传输=UDP`、无“路径”行、
   分辨率 `1920×1080`、异常行不出现。
5. **基线**（netem t≈25 s，等启动升帧结束后）：记录 fps、目标 kbps、
   RTT、帧龄、帧计数。目标码率记为 **B0**。
6. **劣化**（t≈60–85 s）：每 5 s 记录一次，至少 4 个样本；期间在 B
   上做一次点击和一次键入，确认远端仍有响应（允许延迟升高，不应
   完全失效）。
7. **恢复**（t≈120–135 s）：每 5 s 记录一次，至少 3 个样本；
   t≈135 s 在 B 上做键鼠操作与剪贴板双向各一次，确认 1 s 内生效。
8. 留存证据：netem 结束打印的两方向 `received/forwarded/
   loss-dropped/queue-dropped/send-errors/bytes/max-queue`、A 主机
   日志、查看器统计面板截图（或录屏）、可选 CLI 摘要。证据放
   `build\two-machine\`（不入库），测试密码不写入任何文件。

### 判据（所有行同时满足才通过）

| 指标 | 干净基线 | 劣化稳态 | 恢复后 |
| --- | --- | --- | --- |
| 帧率 | 启动后 28–30 fps | 不强制下降：超额延迟 ≥150 ms 时按比例下调，最低 10（Balanced）；码率已无下调空间时才到 5；始终 ≥5 且不断流 | ≥28 fps |
| 目标码率 | 记录 B0（固定 3000 时应为 3000） | ≤0.7×B0（预期 800–1000 kbps） | ≥0.85×B0 且继续回升 |
| RTT | <30 ms | ≥120 ms（注入后基线 160–200 ms；排队时更高，允许到 1000 ms） | <50 ms |
| 帧龄 | ≤150 ms | 稳态 ≤800 ms；降档/关键帧瞬间允许 ≤3500 ms 短峰 | ≤300 ms |
| 分辨率 / 源 | 1920×1080 | 1920×1080 | 1920×1080 |
| 传输 | UDP | UDP | UDP |
| 异常 | 不出现 | 仅允许缺口短时增长且必须停止；CRC 必须为 0（协议错误用 CLI 复核） | 不再增长 |
| 会话 | — | 不断线、不重连 | 不断线；输入 ≤1 s，剪贴板双向正常 |
| 帧计数 | decoded/received ≥99% | 允许丢帧 | 持续解码，无卡死 |
| netem | 干净对照轮 `loss-dropped=0`、`queue-dropped=0` | 主轮汇总至少 `loss-dropped` 非零（证明劣化生效；队列丢弃视自适应速度而定） | 恢复段无新增丢弃（由异常与会话行判断） |

补充判定：

- 目标码率不得在两档之间反复跳变，恢复段必须单调回升。
- 帧龄是查看者用 RTT 探测估计主机时钟偏移后算出的，偏差会让它
  抖动；判读以趋势为主，并用 CLI 摘要的 `max-frame-age` 客观复核。
- 若劣化期 RTT 从未升高、netem 两方向 `forwarded≈received` 且
  `loss-dropped=0`，先查 B 是否走了 VPN/代理或查看者连错主机。
- 出现以下任一项判失败：恢复 45 s 后 fps 仍 <20 或目标仍
  <0.85×B0；分辨率/源尺寸变化；传输回退到 TCP/WebSocket；会话
  重连；恢复后异常计数继续增长。
- 若开启音频：劣化期允许欠载/丢块增加，恢复后不得持续爆音或静音；
  可听质量仍需人工判断。

### 可选：CLI 客观复核

另跑一轮相同 netem，仅用 CLI 连接（避免与 GUI 观看者互相影响）。
B 上执行：

```
build\Release\chast-quic.exe connect --host 127.0.0.1 --port 45434 ^
    --password <测试密码> --insecure --seconds 125
```

`--insecure` 仅用于受信任的测试网络；要校验证书，改为
`--fingerprint <64 位 SHA256>`（查看器统计面板“身份”行或主机日志
里可以读到）。前提是主机认证模式为“密码”。读取接收端摘要：

- `received/decoded`：解码覆盖率 ≥99%，`gaps` 在恢复后不再增长；
- `crc-errors=0`、`decode-errors=0`、`protocol-errors=0`；
- `target-bitrate` 走势与面板“目标”一致（≤0.7×B0，恢复后
  ≥0.85×B0）；
- `max-frame-age` 短峰 ≤3500 ms，结束 `frame-age` ≤300 ms；
- `rtt` 从 ≥120 ms（注入后基线 160–200 ms）回落到 <50 ms，
  `probes/replies` 无长期卡死。

CLI 只覆盖视频与传输；输入、剪贴板与 Flutter 呈现仍以 GUI 步骤
为准。

### 真实无线/热点变体

A 有线、B 走 Wi-Fi 5/6 或手机热点，先测真实链路，再按需叠加
netem。重点观察突发丢包、上下行不对称和信号抖动；判据同上，
RTT 的绝对值改为“实测基线 + 注入延迟”，并记录频段、AP、信号
强度。真实链路若本身没有明显丢包/抖动，再叠加 netem 制造劣化。
