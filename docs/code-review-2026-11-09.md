**R02：监听启动超时分支会把有限等待变成无限等待。**

定位：[Subscribe 的启动等待](D:/ds-chcast/src/clipboard/clipboard_listener.cc:125)。

`WaitForSingleObject(ready, 2000)` 的返回值没有检查，随后直接关闭 `ready`。若监听线程尚未设置 `shared.running`，调用方把线程移到 `failed` 并执行 `failed.join()`。监听线程随后成功创建窗口并进入 `GetMessageW`，此分支却没有发送退出消息；join 因而不会返回。与此同时 `start_mutex` 一直被持有，其他 Subscribe/Unsubscribe 也受阻，调用它的会话线程无法继续。已关闭的 ready 句柄还会被线程用于 `SetEvent`。

本次用已有的私有窗口站测试，唯一注入是在 `CreateWindowExW` 前延迟 2300 ms：正常版本 0.30 秒通过，延迟版本被 CTest 在 7.99 秒终止。探针：[slow_listener.cc](D:/ds-chcast/build/review-standalone-20261109/slow_listener.cc)；日志：[CTest 结果](D:/ds-chcast/build/review-standalone-20261109/out/Testing/Temporary/LastTest.log)。这是故障注入复现，没有声称本机自然出现了两秒窗口创建延迟。

建议用明确的启动/取消状态和可靠的线程停止协议；超时后通知线程退出、处理迟到的窗口创建，并保证 ready 在工作线程不再使用后才关闭。退回轮询必须真的能够返回，不能仅在注释中承诺。

**R05：主机角色密钥仍暴露在命令行。**

定位：[密钥参数](D:/ds-chcast/host/tunnel.cc:231)、[实际进程启动](D:/ds-chcast/host/tunnel.cc:299)。

主机使用 `--host-key <实际值>`，回退时使用 `--server-key <实际值>`，随后直接传给 `CreateProcessW`；只建立了 stdout/stderr 管道，stdin 为空。命令行读取者或启用命令行记录的进程采集系统会得到部署凭据。查看器已通过 stdin 传递连接密钥，Go host CLI 也已有 `--host-key-stdin`，但 C++ 主机入口没有接上。

建议补建仅向子进程继承的 stdin 管道，改用已有的 stdin 参数，写入后关闭；代理凭据和设备秘密也应采用同一机制。角色密钥限制了服务端用途，但不会让泄露的注册凭据变得无害。没有声称仅凭 host_key 即可伪造现有设备的独立签名。

**D01：不能把注册凭据变成全部署授权签发权。**

定位：[G02 票据草案](D:/ds-chcast/docs/status-and-plan-2026-11-09.md:43)。

目前 `host_key` 是部署级的共享角色凭据，安装在受控主机上。草案让它作为票据 HMAC 密钥：任何持有该密钥的主机都可以为任意 `hostId`、用户和权限掩码生成可验证的票据；域分离只区分用途，不能区分同一密钥的持有者。即使尚需通过本地主机密码/审批，这也已经绕过中央 ACL 的连接资格判断。

建议使用独立的服务端票据签发密钥，主机固定相应公钥；可参考项目已有的 [Ed25519 身份与签名实现](D:/ds-chcast/server/internal/identity/identity.go:91)，但应为访问授权定义独立用途、密钥标识和轮换规则。票据至少绑定 issuer、主机身份（避免 ID 复用）、subject、权限上限、有效期、策略版本和唯一 ID。若暂用每设备独立 MAC，也必须重新设计分发/撤销，不能复用部署级 host_key。

**D02：账号禁用与移组不能只在新 lookup 上生效。**

定位：[离线验签与 Hello 校验](D:/ds-chcast/docs/status-and-plan-2026-11-09.md:43)、[验收承诺](D:/ds-chcast/docs/status-and-plan-2026-11-09.md:46)、[G03 撤权](D:/ds-chcast/docs/status-and-plan-2026-11-09.md:52)。

先领取合法短期票据，再禁用账号/设备或将用户移出允许组，客户端仍可持未过期的旧票据直连；只检查签名与到期时间的离线主机无法得知服务端变更。对已建立会话，Hello 之后没有复核机制，甚至票据到期也不会自动撤销当前操作权。nonce 字段本身也不是重放防护，需要使用状态或明确的会话/客户端绑定。

必须先规定“立即撤权”还是“最多 N 秒生效”。若允许有界延迟，采用短租约、定期授权续租和失败后的断开/降权；若要求更快撤权，还需可靠通知或在线复核及失联策略。测试应包含“先取票再封禁”“保持连接后撤权”“服务端失联”“主机重启与旧票据重用”，不能只测封禁后的新 lookup 被拒绝。

**D03：restricted 生效不能依赖两个配置恰好同时修改。**

定位：[服务端设备策略](D:/ds-chcast/docs/status-and-plan-2026-11-09.md:41)、[本地开关](D:/ds-chcast/docs/status-and-plan-2026-11-09.md:44)。

草案分别增加服务端 `open/restricted` 和本地 `require_access_ticket`，没有说明它们如何建立权威关系。若后台把设备改为 restricted，但本地开关仍关闭，lookup 拒绝并不能阻止知道地址和本地密码的客户端直接连接。旧客户端/旧配置迁移也是同样的绕过窗口。

建议把最小受管策略同步前置到 G02：主机注册时取得并持久化受信任的受管身份/策略版本；受管主机不可因为查询失败或缺配置而退回 open。后台应显示“等待主机应用/已应用”，拒绝把尚未确认的设备标为已经受 ACL 保护。共享主机、服务 worker、直连、UDP/TCP 打洞、relay/carrier 以及各 session mode 都必须进入同一认证守门点。

G02 还应补齐一个链路设计：当前 [TCP agent](D:/ds-chcast/server/internal/agent/tcppunch.go:150) 和 [会合服务](D:/ds-chcast/server/internal/rendezvous/rendezvous.go:400) 仍使用 link/server key 的 HMAC 打洞证明。账号 Bearer token 能 lookup，不代表它能完成现有打洞鉴权。需要明确账号如何取得独立的短期传输凭证，以及 relay/carrier 的续期如何重新检查授权；不能简单把账号 token 填入旧共享密钥字段。
