## 2. 状态口径

| 状态 | 含义 |
| --- | --- |
| 已实现 | 代码路径已经存在，主要行为在源码中可追踪 |
| 自动化通过 | 有本次或对应版本的测试记录，但没有完成真实环境验收 |
| 代码闭环完成 | 数据、服务、传输和必要客户端路径已经接通，但外部环境证据尚未取得 |
| 基本对齐 | 主要业务结果与 RustDesk 对照项接近，仍可能存在覆盖范围或证据缺口 |
| 部分对齐 | 核心路径存在，但产品交互、后端覆盖、稳定性或实机证据不足 |
| 实现完成，待实机验收 | 必要的代码层已经闭环，缺少双机、重启、断网或浏览器证据 |
| 实施中 | 只完成部分层，尚不能作为独立可用功能交付 |
| 待开始 | 尚未完成设计或实现 |
| 条件项目 | 只有产品范围变化时才进入当前批次 |

“已实现”不等于“已完成”。一项功能只有代码、自动化、适用的实机或生产证据全部通过，才能进入正式完成状态。

- 主机签名快照、拉取指令和提交回执 API；
- 指令重试幂等和回执 sequence 校验；
- 指令拉取响应增加服务端签名、timestamp 和 commands digest；
- 服务端公钥验证响应签名的 API 测试。

尚未完成：

1. `delivered` 无回执时可重新拉取；当前只查询 `queued`，HTTP 响应丢失后可能等超时；
2. 管理员 DTO 显式暴露 `receipt_confirmed_absent`；
3. Go 主机代理读取并签名上报原生快照；
4. 代理验证固定服务端身份、host、runtime、时间和指令摘要；
5. 指令先持久化再交给原生端；
6. Windows 原生生成 runtime ID 和 viewer 连接 ID；
7. 多 viewer 有界枚举和按连接 ID 精确断开；
8. 托盘、service 和 tunnel 生命周期接线；
9. 管理台活动连接、详情、断开和状态展示；
10. 多 runtime、重启、断网、旧命令重放和双机实机验收。

管理台最终状态必须严格区分：

- `active`：活动中；
- `stale`：心跳过期，状态未知；
- `closed`：连接已经结束；
- `queued`/`delivered`：命令已排队或已投递，尚未确认执行；
- `applied`：目标主机确认命令已执行；
- `failed`：目标主机明确执行失败；
- `expired`：命令到期未得到可用回执。

只有连接为 `closed`、指令为 `applied` 且收到 `confirmed_absent=true`，管理台才能显示“已确认断开”。控制通道失联或指令过期只能显示未知、待处理或失败。

当前管理员 DTO 尚未显式暴露 `receipt_confirmed_absent`。不能依赖前端从回执文字推断成功，下一步应在服务端增加布尔字段并在 API、管理台和测试中使用。

## 7. 当前性能结论

现有弱网专项条件为 3 Mbps 初始视频、1 Mbps 瓶颈、约 160 ms RTT、双向 3% 丢包。

- 控制器修复后，固定门槛为峰值帧龄 ≤3000 ms、恢复后 ≤300 ms；
- 当前本机记录连续五轮峰值为 1064/1648/1516/1040/1072 ms，结束帧龄 11–19 ms；
- 不限速分支峰值为 1239 ms；
- 修复前 1.5–6.6 秒峰值和宽动态预算只保留为历史定位记录。

这只说明当前内部弱网专项通过，不能证明性能对齐 RustDesk。缺少同硬件、同内容、同分辨率、同编码参数下的 A/B，也缺少真实双机、跨 NAT、IPv6、代理/CDN、跨区域中继、长时间资源增长和生产容量。

## 11. 完成判据

任务只有同时满足以下条件才能标记为“已完成”：

1. 当前源码确实实现，并且缺陷场景有可失败回归；
2. 数据、服务端、传输、主机或查看端、管理台和失败状态形成必要闭环；
3. 鉴权、并发、断网重试、进程重启和旧版本兼容按风险验证；
4. 新持久化对象在 SQLite 和 PostgreSQL 上完成迁移、备份和降级边界验证；
5. 自动化、实机、生产或性能证据分别记录，不互相替代；
6. 附运行版本、命令、日志路径和剩余限制；
7. 发布范围内没有未解决的账号隔离、越权、数据丢失、错误断开或核心连接阻断问题。
