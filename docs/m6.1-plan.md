# M6.1 — 分辨率自适应

状态：已完成（2026-10-22）
上一阶段：M6.0 帧率阶梯与音频预算已完成。
下一阶段：文件传输、音频质量调优。

## 目标

M6.0 之后，弱网下只剩码率和帧率两个杠杆：1080p 在 25% 预算
（约 700 kbps、15 fps）时每像素约 0.023 bit，文字开始糊成块。
这一步补第三个杠杆：**按预算比例降低编码分辨率**，让每一帧的像素
数和可用比特重新匹配。

映射（目标码率 / 上限码率）：

| 比例 | 分辨率 |
| --- | --- |
| ≥ 50% | 100% |
| 30–50% | 75% |
| < 30% | 50% |

与帧率阶梯不同，分辨率档位带 **滞回**：降到 75% 后要回到 ≥55%
才升回 100%，降到 50% 后要回到 ≥34% 才升回 75%。每换一档都要重建
编码器并补一个关键帧，不能在边界上每秒抖动。

缩放必须仍然零拷贝：在采集侧同一个 D3D11 视频处理器里，把 BGRA→NV12
的 blit 的目标矩形改小，图像不出显存、不换卡。

## 非目标

- 用户手动选分辨率/画质档：本轮只有 ABR 自动档。
- 更细的档位（85%、66% 等）与连续缩放：三档足够，档位越多重建越频繁。
- 裁剪/信箱适配：缩放保持源画面宽高比。
- 真机弱网验收：本轮仍是合成样本 + 回环，真机留作人工验收。

## 架构

```
    BitrateController（纯逻辑）
      目标/上限比例 ─→ 分辨率阶梯（带滞回）─→ BitrateDecision
                                                  {bitrate, framerate, resolution_percent}
                                                          │
                        HostServer::sample_link           │
                    ├─ 码率/帧率变：set_rate（同 M6.0）  │
                    ├─ 分辨率变：capturer->set_nv12_scale(percent)
                    │      └─ Nv12Pass 重建：64× 源矩形 → 缩放目标矩形
                    └─ 下一帧：NV12 尺寸变了
                           ├─ create_encoder(新尺寸, 当前 ABR 目标/帧率)
                           ├─ force_keyframe ×2（视图端可能先收到帧后收到公告）
                           └─ refresh_stream（新宽高 + source 尺寸）
```

源尺寸（`ServerInfo::source_width/source_height`）与编码尺寸
（`ServerInfo::width/height`）分开：

- 指针坐标、输入事件、光标精灵比例始终用 **源尺寸**，因此缩放不破坏
  1:1 像素映射；
- `FrameHeader::width/height` 继续描述每个访问单元的实际编码尺寸；
- 查看器用源尺寸做 widget→桌面坐标换算与光标缩放，用编码尺寸决定
  解码器重建。

## 决策

- **缩放放在采集的 NV12 pass**：视频处理器本来就做 BGRA→NV12，
  把目标矩形改小是同一个 blit；BGRA 帧保持原尺寸，dump 工具和参考
  画面不受影响。
- **编码器重建而不是 Reset**：VPL 的 Reset 对分辨率变更支持不一致，
  重建走与初始会话相同的三级回退和 LUID 绑定，行为可预期；重建只在
  跨档时发生，且 ABR 的冷却（降档 1.5 s、升档 3 s + 3 s 健康窗口）
  已经限制了频率。
- **源尺寸进协议**：不改 `width/height` 的既有语义（编码尺寸），
  在 HelloAck/StreamInfo 末尾追加源尺寸，协议版本升 v12。
- **重建失败就固定当前档**：某台机器拒绝某个尺寸时回退到上一档并在
  本会话内停止缩放，不能让编码器每秒重建失败一次。
- **重建后连发两个关键帧**：StreamInfo 与视频帧在不同 QUIC 流上，
  查看者可能先拿到新帧再拿到公告；两个 IDR 保证公告到达后还有一次
  初始化机会，代价可控。

## 验证

- `chast-bitrate-test`：三档映射与两条滞回边界；决策始终携带分辨率；
  严重拥塞下码率、帧率、分辨率同时变化；恢复时逐档回升。
- `chast-protocol-test`：ServerInfo 往返保留源尺寸，截断/零尺寸被拒绝。
- `chast-quic verify`：回环 2.5 s 时默认缩放到 75%（`--resolution N`
  可改），断言
  - 首次 HelloAck 的编码尺寸等于源尺寸（初始 100%）；
  - 缩放后编码尺寸小于源尺寸，源尺寸保持全分辨率；
  - 查看者收到两次 StreamInfo（重公告 + 缩放），描述与运行流一致；
  - 缩放后没有协议错误、每个访问单元都解码，离线重放摘要一致。
- 回归：`ctest -C Release`、`flutter analyze`、`flutter test`、
  `flutter build windows`。
- 人工：`chast-quic serve --resolution 50` + Flutter 查看器，确认缩放后
  指针位置与形状比例仍正确、文字可读、切档瞬间无长时间黑屏。

## 结果（2026-10-22，单机回环）

- 采集：`set_nv12_scale()` 在原 BGRA→NV12 视频处理器上改目标矩形，
  缩放存于显存；`reinitialize()` 保留档位；失败回退上一档并置
  `frame_dirty_` 全量重转。
- 控制器：三档带滞回（100/75/50%），50%→100% 在 ≥55% 时直接回升，
  避免连续两次重建；`BitrateDecision` 始终携带档位。
- 协议 v12：HelloAck/StreamInfo 追加 `source_width/source_height`；
  截断或零尺寸被解析器拒绝。
- 主机：档位变化时先重建编码器、再重公告，失败则固定本会话档位；
  重建后连发两个 IDR，覆盖 StreamInfo 与视频帧的跨流竞争。
- 查看器/Dart：`ViewerStatus` 分开编码尺寸与源尺寸；指针映射、原点
  夹取、光标精灵比例均按源尺寸，`RemoteView` 用编码尺寸决定宽高比与
  绘制；状态浮层在缩放时显示“源 W×H”。
- 验证：`chast-bitrate-test` 分辨率阶梯全部断言通过；
  `chast-protocol-test` 源尺寸往返与拒绝路径通过；`ctest -C Release`
  8/8；`chast-quic verify` 在 1920×1080 源上缩放到 1440×810，121 个
  访问单元全部解码，协议/解码/CRC 错误为 0，离线重放帧数与摘要一致；
  `flutter analyze` 无问题、`flutter test` 全部通过、`flutter build
  windows --release` 成功。
- 人工验收待做：Flutter 查看器内的指针 1:1 与缩放后文字可读性需要一台
  带物理鼠标的机器确认；真机弱网档位轨迹仍需双机测试。

## 已知限制

- 分辨率只随 ABR 决策变化，ABR 每秒采样一次，因此档位变化最多有
  约 1 s 的延迟。
- 缩放使用视频处理器的固定滤波，不是 lanczos；缩小后的文字边缘比
  原生分辨率软。
- 每跨一档重建一次编码器（三级回退 + 测试编码），期间可能丢 1–2 帧。
- 真机弱网（丢包/抖动）下的档位轨迹仍需两台机器人工验收。
