### 1.1 管理台角色与账号登录（2026-10-28）

- 账号角色扩展为四级：`admin`（账号管理 + 全部控制台）、`operator`
  （设备写操作与只读控制台）、`readonly`（只读控制台）、`user`（仅查看器，
  无控制台）。首个账号与旧库最早账号仍自动成为 admin；最后一个 admin
  不能降级、封禁或被删除。
- API 鉴权按三级重写：`/v1/identities`、`/v1/stats`、三类审计列表与 CSV
  导出要求 `readonly` 及以上；`PATCH /v1/identities/{id}`、身份重置、
  `DELETE /v1/hosts/{id}`（移除租约）要求 `operator` 及以上并分别写入
  `device_labels`/`device_reset`/`device_lease_remove` 审计（含操作者
  用户名）；`/v1/accounts*` 只允许 admin 或服务器密钥；`user` 角色一律 403。
  服务器密钥仍是隐式超管，主机注册/查询/指标等 host-only 接口不受影响。
- 内嵌 Web 管理台支持账号登录：登录方式可选“服务器密钥”或“账号”，账号走
  `/v1/account/login`（两步验证码 6 位数字按 TOTP、其他按恢复码提交），
  访问令牌过期自动调 `/v1/account/refresh` 并重试，退出调
  `/v1/account/logout`；`user` 账号登录后立即登出并提示无权限。只读角色
  隐藏设备编辑/重置/移除按钮并显示说明，账号页签仅 admin 可见。
- 创建账号可在一次插入中指定角色；首个账号即使请求其他角色也保持 admin，
  不再出现“账号已创建但接口返回 409”的半成功状态。
- 验证：`TestConsoleRoleMatrix`（4 角色 × 读/写/管理端点）、
  `TestOperatorAndReadonlyRoles`、`TestCreateUserWithRole` 通过；真实
  `chast-server` 回环 + 浏览器用 alice(admin)/bob(operator)/carol(readonly)/

### 2. 账号安全

- **登录失败锁定**（`internal/authlimit`）：按“用户名小写 + 客户端 IP”计数，
  默认 10 分钟窗口内失败 5 次即锁定 1 分钟；成功登录清零。
  - 配置 `--state` 后锁定记录写入 SQLite `login_locks`，跨重启与多实例共享；
    计数通过 `BEGIN IMMEDIATE` 原子累计，避免并发登录丢计数。
  - 管理台 `user unlock <name>` 可手动清除该用户的锁定键；解锁动作写入审计。
  - 通过 `--login-max-failures` / `--login-window` / `--login-lockout` 调整，
    设为 0 可关闭。
- **设备会话**：登录令牌对应可枚举的会话记录；查看器可列出设备、改名、
  撤销单个会话、一键退出其他设备；改密/撤销立即影响后续鉴权。
- **自助改密**：`POST /v1/account/password` 校验旧密码并轮换哈希；查看器提供
  修改密码对话框。
- **邮箱与密码找回**（2026-10-28）：`users.email` 唯一且大小写不敏感，自助
  设置/清空要求当前密码，管理 API 与管理台可代设；`password_resets` 只存

  - 管理台 `user 2fa <name> off` 可重置丢失的 2FA。
- **WebAuthn 安全密钥**（2026-10-28，P2-19/P2-30）：Windows Hello / FIDO2
  平台认证器可作登录第二因素（密码 + 断言）或免密码登录（用户名 + 断言）。

- **令牌生命周期**（2026-10-26）：登录返回 30 min 访问令牌与 720 h 刷新令牌；

### 3. 地址簿

- 服务端地址簿：peer ID、显示名、标签、分组 ID、逐条 `revision`、墓碑；
  支持增量快照（`since`）与分组变更列表，删除保留墓碑供多端合并。
- 分组：创建/改名/删除；删除分组在事务内解绑成员并写分组墓碑；条目只能
  指向存在的分组，失效分组在读取时归一为空。
- 分组嵌套与排序（2026-10-28，账号库迁移 v3）：分组可设置 `parent_id`
  （根为空串，上级须为同一账号的存活分组，成环/深度超 8 拒绝）与
  `position`（非负，按 `position,name,group_id` 排序）；条目也有
  `position`（按 `position,peer_id` 排序）。删除分组时子分组上移到被删组
  的上级、组内条目解绑，各自推进修订，并撤销该分组范围的共享授权；分组
  授权覆盖整棵子树。查看器首页按分组树缩进显示，分组对话框可改上级并用
  上下按钮重排同级，设备菜单支持组内上移/下移。
- 查看器同步：登录后全量/增量合并，保留本地连接参数；标签与分组编辑可离线
  记录意图，恢复在线后上传并撤销意图；删除通过本地 outbox 重试
  （成功/404 清理，401 保留）。
- **条目级乐观并发控制（OCC）**：
  - `PATCH /v1/addressbook/peers/{id}` 接受可选正整数 `if_revision`；
    事务内重新读取修订号与墓碑，令牌不匹配、条目已删除或从未以该令牌存在
    时返回 409 且不写入；`0`/负数返回 400；省略令牌保持最后写入者优先。
  - 查看器 `Device` 持久化 `revision`；同步与即时编辑携带令牌，成功后立即
    写回新修订号。409 时不重试旧值，改为全量拉取并用服务器条目覆盖本地
    （服务器已删除则移除本地行），界面提示“已刷新为服务器版本”，同步摘要
    显示冲突数。
  - 共享地址簿的 `PATCH` / `DELETE .../shared/{owner}/peers/{id}` 同样接受
    `if_revision`（删除用查询参数），与属主写入共用条目修订号；共享编辑
    409 后重新读取共享地址簿并采用服务器行。共享新增在 2026-10-31 补上
    同一保护：`POST .../shared/{owner}/peers` 接受可选正整数 `if_revision`，
    含义是“我上次读到的属主地址簿修订号”（新条目没有自己的条目修订号），
    存储层在同一把写锁内比对 `users.book_revision`，不匹配返回 409 且不
    写入；`0`/负数 400；省略时仍为最后写入者优先以兼容旧客户端。查看器
    共享对话框用 `SharedAddressBook.revision` 作为基线，409 后刷新整本共享
    地址簿并提示“该条目或地址簿已在其他设备修改”。
- **墓碑保留**（2026-10-27）：`--addressbook-tombstone-days`（默认 0 保留全部）
  在启动与每 6 小时删除早于该天数的条目/分组墓碑，管理台 `ab prune <days>`
  可手工执行；存活条目不受影响。离线超过窗口的客户端错过墓碑后需整本快照
  才能收敛，窗口应长于最长预期离线时间。

### 6.1 主机共享目录浏览与按需下载（协议 v30，2026-10-28）

  `ClipboardUpdate` 控制消息的 256 KiB（`kMaxClipboardBytes`），该控制
  消息本身及旧客户端路径保持原样。
- 校验：`valid_clipboard_content` 的 Text 分支只检查非空、无 NUL 与合法
  UTF-8，长度由 `format_limit` 统一约束；Win32 `read_text` 在 UTF-16
  单元数超过上限时直接放弃转换（每单元最多 3 字节 UTF-8），其余交给
  `accepts()` 复验，避免读侧用旧控制消息上限提前拒绝。
- 验证：协议测试新增 4 MiB 恰等可通过、往返一致、4 MiB+1 被拒三项；
  `chast-quic verify` 的模拟主机把更新文本改为 300 KiB（含非 ASCII），
  回环断言查看器收到的文本超过旧 256 KiB 上限。C++ Release 构建通过；
  单独复跑 `protocol` 与 `quic_loopback` 通过（后者 129 项断言）。
  全量 ctest 复跑情况见文首快照。

### 6.6 系统音频 QUIC DATAGRAM（协议 v35，2026-10-31）

- 问题：系统音频走可靠有序的 `CAUD` 流，与视频共享拥塞窗口。视频验收档
  （80 ms + 0–20 ms 抖动 + 3% 丢包 + 1 Mbps）下 QUIC 把抖动当成丢包，
  ABR 降到 500 kbps/10 fps、RTT 235–404 ms；音频包排在视频数据和重传
  之后，0.2–3 s 的迟到把播出余量吃穿，三种排程策略都大量丢块。根因在
  传输层，排程只能补偿一部分。
- 协商：`ClientHello` 末尾追加 capabilities 字节（v35，bit 0
  `kClientCapabilityAudioDatagram`），未知位直接拒绝；`ServerInfo` flags
  新增 `kServerInfoAudioDatagram = 0x1000`，主机只有在音频已启用且
  查看者声明能力时才置位。标志同时出现在 HelloAck 与每次 StreamInfo
  刷新里，查看者以最后一个为准。音频 `AudioHeader` 与 Opus 载荷格式
  不变，仅更换承载。
- 发送：主机在 `announce()` 时锁定模式——要求对端能力、
  `DATAGRAM_STATE_CHANGED` 已报告发送开启、
  `MaxSendLength ≥ AudioHeader + 512` 字节，
  并在可靠音频流上发送一次 `CAUD` 魔数（失败则整场回退可靠流）。魔数
  让查看者沿用现有的 4 字节流分类，同时保留该流的 FIN 语义：音频关闭时
  FIN 仍能结束该路音频。之后 `send_audio` 直接调用 `DatagramSend`；
  应用持有缓冲直到 `DATAGRAM_SEND_STATE_CHANGED` 报告最终状态，
  连接关闭时统一释放。DATAGRAM 超预算或发送队列满返回 `WaitTimeout`，
  主机按“短丢包”计数，不停止音频。
- 接收：查看者优先排空 `DATAGRAM_RECEIVED` 队列（上限 256 包，溢出
  丢最旧），队列为空再读可靠流，因此回退与收尾共用同一路径。DATAGRAM
  可能丢失或重排：CLI 以序号前跳计 `gaps/missing`、后退计 `reordered`，
  回环要求丢包 ≤2%、弱网 ≤10%；短缺口由 §6.7 的 Opus PLC 补齐。
  可靠流 FIN 到达时，如果 DATAGRAM 模式开启且流上只剩 ≤4 字节
  魔数，查看者在报告“音频结束”前等待最多 150 ms，让 FIN 之后仍在途的
  数据报落地；正常会话该等待不会发生。
- 回退：旧查看者不声明能力 → 主机不置位、继续可靠流；DATAGRAM 扩展
  未协商成功（`DatagramReceiveEnabled` 关闭、路径预算不足、魔数发送
  失败）→ 同样走可靠流。查看者的 `QuicClientConfig::audio_datagram`
  默认开启；CLI `--audio-stream` 仅用于 A/B 对照与极小路径。
- 验证（2026-10-31，单机回环）：`chast-quic verify --audio` 覆盖合成
  音频，断言 DATAGRAM 已协商、200/200 包、FIN 与解码时长；`ctest -R
  "^(protocol|audio|audio_dsp|quic_loopback)$"` 4/4 通过，既有视频
  `quic_weak_network` 仍通过。视频验收档 25 s 的 A/B（`verify --netem
  --audio`）：DATAGRAM 1248/1251（0.24% 丢、解码 24.95 s），可靠流
  1250/1250（24.99 s）。带 WASAPI 播放（`--play`）：DATAGRAM
  1212/1249（2.96% 丢、解码 24.23 s、欠载 1、丢块 368、slack
  −1026..+23 ms、均值 −99.5 ms、av-skew +30.2 ms），可靠流
  1250/1250（24.99 s、欠载 1、丢块 407、slack −5934..+15 ms、均值
  −882.4 ms、av-skew +26.0 ms）。同一链路下 DATAGRAM 把平均迟到从
  约 0.88 s 压到约 0.1 s、最差从 5.9 s 压到 1.0 s，正是本专项要消除的
  拥塞拖尾；代价是 3% 丢包下少数包不再重传。
- 边界：丢包隐藏已由 §6.7 的 Opus PLC 补齐（每次前跳最多 5 帧）；
  按抖动自适应的接收缓冲已由 §6.8 实验实现，空转指标显示实际静默
  低于默认，但仍保持默认关闭（2026-10-31 已补起播/重锚宽限，仍差
  双机听感受限）。单次 A/B
  受 CPU 负载影响，2.96% 与
  0.24% 的差异主要来自丢包注入随机性。双机真实无线、NAT/PMTU 与
  Flutter 播放路径待验（GUI 查看器默认使用 DATAGRAM，无需额外开关）。

### 6.7 系统音频丢包隐藏（Opus PLC，2026-10-31）

- 问题：v35 把系统音频改走 DATAGRAM 后丢包不再重传，缺口只是一段
  20 ms 静音。视频验收档 25 s 内每次有 8–13 个包真正丢失、18–19 个
  序号前跳，解码时间线与计数都会出现空洞。
- 解码器：`IAudioDecoder` 新增 `conceal(next, frames_back, out)`。Opus
  用 `opus_decode(decoder, nullptr, 0, ...)` 的内建 PLC 合成一帧；没有
  已解码历史、帧长超过 120 ms 或格式不符时返回错误；AAC（仅旧录像）
  返回 `Unsupported`。隐藏块的捕获时间取
  `next.capture_ms - frames_back × 帧长`，`pts_ms` 与正常解码同一公式，
  因此占据丢失包原本的时间线槽位；每次合成同时推进 `audible_frames_`，
  连续补多帧时逐帧向前。
- 接收：CLI `drain_audio` 与 GUI 查看器都维护 `expected_seq`。序号前跳
  时最多补 5 帧（100 ms），更长的断流保持静音；序号后退的迟到包直接
  丢弃（槽位已由隐藏帧覆盖），不再倒放。CLI 新增 `concealed` 统计，
  接收摘要与弱网输出都打印；`verify` 断言隐藏帧数不超过缺口帧数。
- 验证（2026-10-31）：
  - `chast-audio-codec-test` 新增 15 项断言：丢失一包后隐藏块为 1 个
    20 ms/声道帧、`capture_ms` 等于丢失包、`pts_ms` 与“同状态参考解
    码器直接解码该包”完全一致、能量 0.355（非静音）、之后仍能正常
    解码，以及无历史时拒绝隐藏、零偏移被拒绝。
  - `cmake --build build --config Release` 全量通过；
    `ctest -R "^(protocol|audio|audio_dsp|quic_loopback|quic_weak_network)$"`
    5/5 通过（约 1 分钟）。
  - 视频验收档 25 s（`verify --netem --audio`）：发送 1253、接收 1245
    （0.64% 丢）、gaps 18、reordered 22、missing 30、concealed 30、
    解码 25.05 s、0 CRC/解码错误，弱网全项通过。两次 `--play`：
    1241/1252（0.88% 丢，missing/concealed 39/39，解码 25.03 s，
    欠载 1、丢块 400、slack −615..+42 ms 均值 −35.3、av-skew +56.2 ms）
    与 1237/1250（1.04% 丢，32/32，24.99 s，欠载 2、丢块 403、
    slack −462..+28 ms 均值 −47.2、av-skew +41.5 ms）。同档可靠流
    对照 1250/1250、0 缺口、解码 24.99 s、欠载 1、丢块 406、slack
    −7575..+12 ms 均值 −1187.5、av-skew +27.7 ms。
- 边界：`missing` 按序号前跳计，包含随后到达但已过槽位的重排包，
  因此 30–39 大于真正丢包数（8–13）；`concealed` 与它相等说明每个
  前跳缺口都在 5 帧内补齐。0 lead 的到达锚定下，隐藏帧的槽位通常已
  经过去，播放器按既有规则丢弃过期块，所以 PLC 保证的是解码输出与
  计数连续、并在有排程余量（成串到达或未来引入 lead）时可听；欠载
  与丢块仍与加 PLC 前同一量级（1 对 1–2、368–407 对 400–403）。音乐
  级连续的自适应抖动缓冲已由 §6.8 实验实现（默认关闭）。

### 6.8 系统音频自适应抖动缓冲（实验，2026-10-31）

- 问题：0 lead 的到达锚定在链路时延阶跃（netem 在会话第 4 s 注入
  80 ms 时延）后没有排程余量。视频验收档 25 s 内接收约 1250 块，
  默认播放器丢弃 374–406 块（约 30%，合 7.5–8.1 s 音频），只剩
  805–814k 帧真正写入端点。
- 控制器：`JitterLeadController`（`include/chast/audio.h`）。按 500 ms
  窗口观察每块 `slack = 排程播放时刻 − 到达时刻`；窗口内至少 2 块
  slack ≤ −20 ms 时抬升 lead，步长 = 缺口 + 10 ms、单窗 ≤40 ms、
  上限 120 ms；连续 2 个窗口内每块 slack > +20 ms 后，每窗回收
  20 ms；中间区间保持不变。每窗口至多一次变更，单个乱序包不会让
  lead 来回抖动。窗口开始于起播后 1 s 内或停顿重锚后 0.5 s 内时
  不抬升也不回收：这两段是队列填充/恢复突发，不代表链路抖动
  （2026-10-31 补，见下）。
- 播放器：`AudioPlayerConfig::adaptive_jitter`。lead 在入队时**逐块
  固定**（`Block::play_lead_ms`），渲染按块自己的 lead 排程，抬升不会
  把已经入队或已写入端点的块再次推后（早期全局 lead 版本正是因此把
  欠载从 1–2 抬到 19–20，已废弃）。`>100 ms` 停顿重锚时
  `JitterLeadController::release()` 清零 lead、保留会话计数并重开
  窗口，恢复最低时延。`AudioPlayerStats` 新增
  `jitter_ms / jitter_raises / jitter_decays`，CLI 播放行打印
  `jit=… (+raises/-decays)`；`verify --netem --audio --play
  --adaptive-jitter`（隐含前两个开关）用于 A/B。
- 端点空转指标（2026-10-31）：`AudioPlayerStats::starved_ms` 在渲染
  线程按调度时间线累计相邻已写入块之间的静默（后块起点晚于前块
  结束的毫秒数），与渲染唤醒频率无关：整块丢块、队列截断和迟到
  产生的空洞各计一次，端点重建重置时间线但不重置会话累计。CLI
  播放行与弱网汇总打印 `starved=… ms`。它把默认模式“一直在丢块却
  只记 1–2 次欠载”的盲区量化出来：25 s 采样中丢块 393–399（每块
  20 ms）对应空转 7980–8000 ms，两者吻合。
- 查看器浮层遥测（2026-10-31）：`ViewerStatus` 新增
  `audio_starved_ms/audio_dropped`，`viewer_bridge.cc` 暴露
  `audioStarvedMs/audioDropped`，Flutter `ViewerStatus` 解析并在
  统计浮层“音画”行显示 `空转 … ms · 丢 …`（英文
  `starved … ms · dropped …`）。GUI 播放路径仍用 0 lead，浮层读数
  用于双机验收对比；新增中英文浮层组件测试，`flutter analyze` 无问题、
  全量 423 项测试通过、Windows Release 构建通过。
- 单测：`chast-audio-playout-test` 28 项断言，覆盖干净链路零 lead、
  单窗步长与 120 ms 上限、自定义上限与 margin、单块迟到忽略、
  ±20 ms 中性区、2 窗保持后每窗回收、起播/停顿宽限内不抬升、
  release 保留计数与 reset 清零；
  `ctest -C Release -R "^(audio|audio_dsp|audio_playout|protocol|
  quic_loopback|quic_weak_network)$"` 6/6 通过（约 60 s）；全量串行
  ctest 38/38 通过（567.83 s，2026-10-31 宽限后复跑）。
- A/B（视频验收档 25 s，同一构建；每组 6–10 次采样，取范围与中位数）：

| 配置 | 播出帧 | 欠载 | 丢块 | slack 均值 | jit 终值 | av-skew |
| --- | --- | --- | --- | --- | --- | --- |
| 默认（0 lead） | 805–814k | 1–2 | 374–406 | −97…−107 ms | 0 | +30…+37 ms |
| `--adaptive-jitter` | 835–946k | 1–13（中位 11.5） | 260–365 | −39…−59 ms | 0–20 ms（峰值 120） | +27…+52 ms |

  每次运行控制器都在劣化窗口内抬升 3 次到 120 ms、恢复后回收 5–6 次；
  播出帧中位数约 +10%（范围 +3…+17%），丢块中位数约 −24%
  （范围 −10…−36%）。
- 空转复测（2026-10-31 起播宽限 + 2 窗回收后，同一构建）：弱网验收
  档 25 s 默认 `starved=7960 ms`、播出 814k 帧、丢块 397；自适应
  三次采样 `starved=8000/6160/6020 ms`、播出 817k/906k/912k 帧、
  丢块 371/302/295；两次采样把实际静默缩短约 23–24%、播出帧提高
  约 11–12%，一次与默认持平（采样噪声）。4 s 干净回环中宽限生效：
  自适应 lead 80–120 ms → 40 ms（raises=3→1），skew +127/+123/
  +154 ms → +84/+76/+91 ms，默认同构建为 +33…+40 ms；25 s 干净
  链路自适应 `jit=20 ms`（raises=1、decays=1）、skew +60.7 ms，
  默认 +44.6 ms。
- 判定：宽限消除了短会话的 120 ms 钉死，弱网连续性维持原收益；
  但干净链路自适应仍保留一个 20–40 ms 的 lead（到达锚定下 30 fps
  视频节拍内的块间排程差），skew 比默认高约 16–40 ms。因此保持
  **默认关闭**，仅保留 CLI 实验开关，转默认仍差双机可听验收；
  若要进一步收敛干净链路时延，应把音频块按发送侧排程时刻播放
  （或固定一帧节拍的 lead），而不是继续微调控制器。GUI 查看器
  （`viewer_engine.cc`）继续使用 0 lead，Flutter 播放路径未改。
- 计数口径说明：trace 显示自适应的欠载都发生在 lead 已到顶或正在
  爬升、而平均 slack 仍为 −50 ms 左右时；恢复后 jit 回落到 0–20 ms，
  这几次采样中没有触发 `>100 ms` 停顿重锚。默认模式则把连续迟到的
  块整块丢弃，丢弃不会更新 `last_end_local_ms_`，而欠载检查要求该值
  非零并在触发后清零，因此“一直在丢块”的流反而只能记到 1–2 次
  欠载——`starved_ms` 就是为消除这个盲区而加，现已进入 CLI 播放行
  与弱网汇总。
- 后续若要降低该档欠载：在控制器饱和且窗口仍迟到时把锚点前移到
  当前到达（一次跳过积压再恢复 120 ms 余量），或提高上限换取更大
  时延；两者都会改变 A/V 延迟，需与双机可听验收一起定。

### 6.9 系统音频包级冗余评估（2026-10-31，不采用）

- 背景：v35 DATAGRAM 音频在视频验收档仍有约 0.2–1% 丢包，§6.7 的
  PLC 只保证解码与计数连续；0 lead 下过期隐藏块通常不可听，音乐级
  连续需要更早的修复或抖动余量，因此评估两条包级冗余路线。
- Opus 带内 FEC 排除：Opus 的 FEC 只存在于 SILK/LPC 模式（RFC 6716
  §2.1.4）；`OPUS_SET_INBAND_FEC(1)` 会把 CELT 音乐模式强制切到
  SILK 并明显降低质量，`FEC=2` 保持 CELT 但没有冗余（抓包头部证实
  无 LBRR 帧）。还原路由的麦克风本就走可靠流，故不做。
- 1+1 DATAGRAM 复制已实现并验证（临时特性）：主机 `send_audio` 在
  同一时刻把同一包发两次、序号不变；干净回环收到 400/200、
  `reordered=200`、0 CRC/解码错误，机制本身工作。
- 弱网 A/B（视频验收档 25 s：80 ms 时延 + 20 ms 抖动 + 3% 丢包 +
  1 Mbps）：

| 配置 | 发送 | 接收 | reordered | missing | concealed | 主机丢弃 | 解码 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 基线 #1 | 1252 | 1233 | 21 | 40 | 30 | 0 | 24.83 s |
| 1+1 #1 | 1249 | 2450 | 1252 | 51 | 51 | 0 | 24.99 s |
| 1+1 #2 | 1252 | 2428 | — | 52 | 52 | 0 | — |

- 另两组（抖动 2 ms）：8% 丢包 + 1 Mbps 档基线 missing 40/39、
  concealed 37/39（两次），1+1 为 33/42、33/42，处于噪声区间；纯
  丢包档（8% 丢包、关闭限速）基线 sent 1253 / recv 1212 / missing 45
  / concealed 44，1+1 sent 1249 / recv 2426 / missing 29 /
  concealed 29，仅该档略好。
- 根因：MsQuic 把背靠背排队的两个 DATAGRAM 帧合并进同一个 UDP
  数据报，两副本共享丢包命运。证据：默认档 `received − reordered ≈
  sent`，几乎每份副本都到达但都记为重排；纯丢包档中继侧
  host→viewer 的 UDP 数据报只从 3006 增到 3170（+164），而副本约
  1250 份——约 87% 的副本与原包合并进同一个 UDP 数据报。
  `host drops=0` 说明丢包发生在链路，不是主机发送队列。
- 结论：1+1 在本栈上无效且默认档更差（多一份流量加剧中继排队），
  已完整回退：配置字段、传输分支、CLI `--audio-redundancy` 与临时
  ctest 均已删除。默认保持单副本 DATAGRAM + PLC + 可选自适应 lead。
- 保留的评测设施：`verify --netem` 新增 `--netem-delay-ms`、
  `--netem-jitter-ms`、`--netem-loss-percent`、`--netem-rate-kbps`
  （0 关闭限速，便于纯丢包探针）；自定义档跳过 ABR 断言并打印
  `profile: custom --netem values; ABR assertions skipped`；弱网音频
  行新增 `host drops`。
- 后续若要包级修复：副本必须落在不同的 UDP 数据报，例如发送端把
  修复副本延迟 5–10 ms 再发，或做交织奇偶校验 FEC（每 N 包一个修复

  需与双机可听验收一起评估；当前先按 §6.8 的自适应 lead 路线处理
  连续性。

### 6.10 发送侧固定 lead 排程 A/B（实验，2026-10-31）

- 背景：§6.8 的结论建议用“按发送侧排程时刻播放”收敛干净链路的
  20–40 ms 残余 lead，而不是继续调控制器。播放器本就支持
  capture-anchored 模式（`arrival_anchored=false`、`lead_ms`、
  `set_clock_offset`），但 CLI 未暴露，无法 A/B。
- 设施：`chast-quic connect|verify ... --play` 新增
  `--audio-capture-anchor`（固定 40 ms）与 `--audio-lead-ms N`
  （1–500 ms，隐含 capture anchor）。该模式按主机采集时间戳加
  固定 lead 排程，时钟偏移来自首个 LatencyReply；可与
  `--adaptive-jitter` 组合，此时 `lead_ms` 是底，控制器在其上
  再加最多 120 ms。
- 洁净链路（零损伤自定义中继档，12 s，单次采样）：到达锚定
  starved 0 ms / 播出 1,190,400 帧 / 丢 4 / skew +34.9 ms；
  固定 40 ms 为 27 ms / 1,197,768 / 1 / +29.9 ms；固定 80 ms
  为 7 ms / 1,199,688 / 0 / +69.3 ms。固定 40 ms 在洁净链路上
  不增加甚至略降 skew，丢块更少。**40 ms 底 + 自适应**在 12 s
  与 25 s 两次均为 starved 27 ms、丢 1、jit 0，skew +26.7/+26.2 ms，
  是洁净档最优。
- 弱网验收档（80 ms + 20 ms 抖动 + 3% 丢包 + 1 Mbps，25 s）：

| 模式 | starved | 播出帧 | 丢块 | underruns | skew |
| --- | --- | --- | --- | --- | --- |
| 到达锚定（默认） | 7980 ms | 812,160 | 399 | 1 | +32.1 ms |
| 自适应（`--adaptive-jitter`） | 6520 ms | 888,000 | 312 | 11 | +45.6 ms |
| 固定 40 ms | 8335 ms | 812,808 | 405 | 1 | +33.1 ms |
| 固定 80 ms | 6739 ms | 886,248 | 302 | 3 | +74.3 ms |
| 固定 120 ms（两次） | 3960/4435 ms | 1,015,368/990,888 | 193/212 | 3/2 | +113.4/+112.3 ms |
| 固定 160 ms | 3246 ms | 1,048,968 | 155 | 9 | +153.7 ms |
| 40 ms 底 + 自适应（两次） | 6390/4034 ms | 906,408/1,015,848 | 308/191 | 7/4 | +32.6/+33.9 ms |

  固定 lead 的连续性随 lead 单调改善，skew 同步增加；自适应在约
  120 ms 上限内用 6.5 s 空转换取 +45.6 ms skew，固定 120 ms 用
  +112 ms 换 4.0–4.4 s。组合模式从 40 ms 底开始，劣化窗口内
  抬升 3 次到 160 ms 总 lead、恢复后回收 6 次，弱网空转 4.0–6.4 s
  与纯自适应同档或更好，skew 却只在 +33 左右。
- 判定：固定 40 ms 是洁净链路不增时延的候选；“40 ms 底 + 自适应”
  同时拿到洁净 +26 ms skew 和弱网 4.0–6.4 s 连续性，是 GUI 默认的
  首选候选，但弱网样本波动大、还需双机可听验收。暂不改 GUI/CLI
  默认（仍为到达锚定），实验开关保留供复现。
- 验证：控制器观测扩展到两种时间线后，`cmake --build build --config
  Release` 通过，`ctest --test-dir build -C Release -R
  "^(audio|audio_dsp|audio_playout|quic_loopback|quic_weak_network)$"`
  5/5 通过（58.74 s）。默认路径行为未变（到达锚定且未开
  `--adaptive-jitter` 时控制器不参与）。

### 6.11 长期时钟漂移校正（实验，2026-10-31）

- 背景：capture-anchored 排程假定主机采集时钟与查看者本地时钟同速。
  长会话或廉价声卡的 ppm 级偏差会逐渐吃光固定 lead（晚漂移），或让
  时延线性增长（早漂移）。§6.10 的组合模式仍没有稳态校正。
- 控制器：`PlayoutDriftController` 以 5 s 窗口记录“最佳到达相位”
  （slack 的最大值，等价最小单向时延），第一个窗口只预热不学习；
  偏离参考超过 ±15 ms 且连续 2 窗确认后，每窗最多改 20 ms 时钟偏移
  （正=提前播放），持续偏离时不再重新确认；端点重建或基础偏移变化
  超过 50 ms 时 reset。窗口取最大值，使一次积压突发（最老块相位极低）
  无法污染参考；玩家观测前减去 lead，自适应 lead 的抬升不会被误判为
  漂移。仅 capture-anchored 生效，到达锚定忽略，默认关闭。
- CLI：`--audio-drift-correction` 与 `--audio-drift-ppm N`
  （-5000..5000，合成主机时钟漂移，按块 capture 相对首块计算，
  启动/解码延迟不计入），播放行新增 `drift=±N ms steps=N`。
- 60 s / lead 120 ms / −2000 ppm（累计 −120 ms）单机回环：

| 工况 | 播出帧 | 丢块 | starved | underruns | slack 均值 | drift/steps |
| --- | --- | --- | --- | --- | --- | --- |
| 无校正 | 2,230,248（46.5 s） | 675 | 9491 ms | 108 | +10.9 ms | 0/0 |
| 校正 | 2,850,888（59.4 s） | 29 | 666 ms | 2 | +42.5 ms | −80 ms/4 |
| 洁净对照（无 ppm，开校正） | 900,168（18.8 s） | 60 | 1187 ms | 4 | +51.6 ms | 0/0 |

  无校正时漂移越过 120 ms lead 后时间线停摆，丢 6.75 s、空转 9.5 s；
  校正用 4 步 −80 ms 把相位维持在参考附近，丢块回到洁净档水平
  （29 对 60）。本机回环管线本身约占 40 ms：lead 40 ms 时真实余量
  接近 0，任何负漂移都会立即丢块，这也是早期 25 s A/B 病态的原因，
  随后改用 120 ms lead。
- 单测：`audio_playout` 新增 9 项漂移用例（稳定、死区、晚/早、
  单离群、启动突发、预热、步长上限、reset），全套 40 项通过。
- 验证：`cmake --build build --config Release` 通过；聚焦 ctest 5/5
  （59.87 s），随后全量 ctest 38/38（560.43 s）；接入静音门控配置
  （`--audio-silence-gate-ms`）与进程级重启探针后再次全量串行 ctest
  38/38 通过（566.36 s，2026-10-31，exit 0，`quic_weak_network` 收官）。10 分钟长会话 soak
  （`serve`+`connect` 回环、密码模式、lead 120 ms、−300 ppm，查看器
  运行 619.99 s）：播出 29,759,520 帧、丢 1 块、空转 111 ms、
  underrun 0、slack 均值 +75.4 ms（+0…+196）、DATAGRAM 31,000 包
  0 丢/0 乱序/0 隐藏、drift=−180 ms/10 步（理论 −186 ms），说明控制器
  在 10 分钟量级稳定跟踪且不丢时间线。固定 120 ms lead 使 A/V skew
  达 +283.8 ms，属测试专用，GUI 仍用到达锚定。
- 10 分钟洁净对照（同参数、无 `--audio-drift-ppm`、开校正，查看器
  600 s / 主机 620 s）：播出 26,365,128 帧（549.3 s），DATAGRAM
  27,472 包 0 丢/0 乱序/0 隐藏，drift=+0 ms/0 步，A/V skew +87.7 ms；
  丢 8 块、starved 70,621 ms、underrun 4。主机静音门控在会话中开关

  549.3 s 播出 + 70.6 s 空转 ≈ 620 s，说明空转是主机静音而非传输
  丢失；跨过门控数据缺口控制器仍零误校正，这是洁净链路的核心验收点。
- 静音门控此前只有 `LoopbackCaptureConfig::silence_gate_ms` 默认值，
  无任何配置路径；2026-10-31 接通 `HostServerConfig::audio_silence_gate_ms`

## 已知限制 / 与 RustDesk 的剩余缺口

### 地址簿

- 条目级与分组级 OCC 已覆盖自有地址簿、共享编辑/删除与分组改名/删除；
  共享新增已在 2026-10-31 接受属主地址簿修订号作为基线（省略时仍为最后写入者
  优先；新条目没有可比较的条目修订号）。
- 已支持按分组共享与分组级 ACL（2026-10-26）：授权可选 `group_id`，读取按
  范围过滤，读写只作用于该分组；整本授权仍覆盖全部条目。共享条目不复制到
  被授权者自己的地址簿。
- 地址簿不保存任何凭据：共享条目没有密码，也没有设备 hash。RustDesk 的
  服务端地址簿（`flutter/lib/models/ab_model.dart` 的 `_serialize`）同步
  `toCustomJson(includingHash: true)`，只含 peer 的 `hash`，密码不在其中；
  `Peer.toJson` 的密码只进本机地址簿缓存。chast 的受信设备保存在主机侧
  `TrustStore`，地址簿只负责分组与共享；被授权者连接目标仍需目标主机
  自己的密码与审批。
- RustDesk 没有地址簿导入/导出（`flutter/lib/common/widgets/address_book.dart`
  的菜单只有添加/分组/标签等），chast 也不提供；如日后要加，属于本地备份
  便利功能，不是对齐项。
- 分组支持嵌套、按钮式上下排序与同层拖拽排序（2026-10-31，P2-53：每行
  拖动手柄拖到同层分组即换位，跨层拖拽被忽略，写回仍按 1..n 位置与逐条
  `ifRevision` OCC）；设备卡片可拖到分组标题直接移入该组（2026-10-31，
  P2-54：服务端图标作拖动柄，只接受本服已登录账号的条目且目标组不同于
  当前组，写本地后按条目 `ifRevision` 上传，失败保留本地待同步；2026-10-31
  P2-57 起未分组为空时也保留“未分组”标题作为拖出分组的投放目标）；同组卡片之间可互相拖拽排序（2026-10-31，
  P2-55：拖到另一张卡片即插入其位置，写回与菜单上下移共用 `_applyPeerOrder`
  的 1..n 位置与逐条 `ifRevision`，跨组拖拽仍只认分组标题）；分组名随账号会话
  持久化（2026-10-31，P2-49），重启后首次同步按会话里的修订号增量读取，
  只有新登录、旧版会话或空分组列表才全量读取；登出/过期会连同会话一起清除。
  分组折叠状态跨重启保存（2026-10-31，P2-52：与标签筛选共用
  `%APPDATA%\chast\ui-filter.json` 的 `collapsed` 键，写入时合并、互不覆盖；
  分组被删除或换服后旧 ID 自然不再匹配）。
- 地址簿只保存 peer ID、名称、标签与分组 ID，不保存连接参数；搜索/筛选
  覆盖“我的设备”与共享地址簿对话框（2026-10-31，P2-50：按名称/ID/标签
  大小写不敏感过滤，无匹配的属主整组隐藏，计数随筛选变化），“我的设备”
  的搜索词还匹配分组名及祖先组名，筛选期间折叠分组自动展开、清空后恢复
  原折叠（2026-10-31，P2-56；折叠集合不被修改），仍不支持拼音/模糊匹配；
  “我的设备”的标签筛选跨重启保存（2026-10-31，P2-51：
  选中标签存于 `%APPDATA%\chast\ui-filter.json`，启动即恢复，文件损坏或
  标签已不存在时按“全部”处理），搜索框文本与共享地址簿搜索词仍不持久化。
- Wake-on-LAN 的 MAC 仅本地保存，不同步；仅同网段直发。这是 RustDesk 的
  同等行为（`src/lan.rs` 的 `send_wol` 也只对局域网发现得到的 IPv4 发
  `wol::send_wol`）。

### 账号与安全

- 访问令牌与刷新令牌以 DPAPI 信封保存在 `account.json`（2026-10-30，见上文），
  刷新令牌每次续期轮换；刷新响应丢失（如断网）后，查看器下一轮用旧令牌重试，
  只要在轮换后 2 分钟内且服务器刚发出的替换令牌从未被使用，服务端会作废那份
  从未送达的令牌并再发一对新令牌（2026-10-31，P2-58，`RefreshReuseGrace`），
  替换令牌已被使用或超出窗口仍按重放撤销整个会话并需要重新登录；同一旧令牌
  只能用一次，恢复后的下一次重放即触发吊销。查看器的地址簿接口收到 401 时也先
  用刷新令牌强制续期一次，只有续期被拒才退出登录（2026-10-31，P2-58；
  访问令牌本地过期但会话仍可续期时同样先续期再同步）。无桥接的 `dart run`
  工具仍按旧明文格式读写，便于离线脚本。
- 有登录失败锁定与解锁，登录审计记录客户端 IP；配置 `--geoip-file` 时另写入
  离线表给出的登录地点（管理台审计与查看器设备会话展示），未配置时只记录
  IP。账号可持久封禁（吊销全部令牌，密码正确也拒绝登录），但封禁只按账号，
  没有按 IP/设备的账号级黑名单。
- 支持 TOTP、恢复码、短信登录码与邮件登录码（2026-10-28 P2-17/P2-18，需先
  分别绑定找回手机/邮箱）；邮箱与短信找回已支持（API、管理台与查看器登录页/
  账号对话框，邮件走 SMTP 或线下令牌、短信走通用 HTTP 网关）；WebAuthn 安全
  密钥已于 2026-10-28 补齐（P2-19/P2-30，密码 + 断言或免密码断言，
  Windows Hello/FIDO2，查看器账号对话框与两种登录入口均已接入，真实弹窗
  保留人工验收）。
- 账号标签只是逐设备标签，没有按组授权。

  上报，按 `audit_ref` 合并）；但仍没有地理位置或服务端抓包核对，查看器
  文件传输按轮询窗口聚合（主机侧逐文件）。三类运营者历史（账号安全审计、
  连接、文件传输）均可用 `format=csv` 流式导出（2026-10-28，P2-24），沿用
  `action`/`username`/`host` 过滤。
- 审计保留支持条数上限与时间清理（`--audit-retention-days` /
  `audit prune`），并支持 CSV 流式分页导出与 `--audit-archive-dir` 外部
  JSONL 归档（2026-10-28，P2-24，检查点持久化、重启续写、至少一次语义）。
  归档已支持按 UTC 日轮转、关闭日 gzip 与 `--audit-archive-retention-days`
  定时删除（2026-10-30，P2-38），并支持把已关闭文件 HTTP PUT 到远端
  （2026-10-30，P2-44：`--audit-archive-remote`/`--audit-archive-remote-token`、
  `X-Chast-Audit-Sha256`、`.delivered` 标记、每文件每轮 3 次重试；启用投递后
  保留清理只删除已投递文件）；S3 兼容端点由服务器直接做 SigV4 签名投递
  （2026-10-31，P2-46：`--audit-archive-s3-*`、path-style 或
  `--audit-archive-s3-addressing virtual`、`X-Amz-*` 头、
  可选会话令牌，与 HTTP 投递互斥）；仍没有集中去重队列（未送达的证据留在
  本地等下一轮），迟到合并的主机审计不会回写旧日文件。
- 主机自报元数据未签名。软件更新可由服务端在 `/software/{name}` 托管并用
  服务器身份签名（`--software-dir`，通告附 SHA-256/大小）；主机代理在显式
  开启 `--auto-update` 且固定 `--server-pubkey` 时会校验、暂存并启动安装器
  （2026-10-28，P2-22）；查看器在固定服务器身份后可通过
  `chast-tunnel apply-update` 下载、换入并重启自身（2026-10-28，P2-27）。

  常驻的回滚机制（启动失败仅即时还原）。
- tracing 只覆盖 HTTP 请求（会合 API 与节点控制面），没有中继/会合数据面、
  SQLite 或队列深度的 span，也未实现 OTLP/gRPC；采样率与 collector 端点
  需重启生效。
- HTTPS 可要求 mTLS 并支持私有 CA（服务端/节点/代理/隧道/节点池）；服务端
  与中继会热加载替换后的证书/私钥文件，证书可由内建 ACME（`--acme-domain`，
  HTTP-01）自动申请与续期，也可继续用文件证书或外部工具（如 certbot）；
  证书与 `--tls-client-ca` 均支持热加载（2026-10-28，P2-26）；只在回环用
  临时 CA、自签证书与预置缓存验证过，真实企业 CA 链与真实 CA 签发未测。
- Web 管理台可用 server-key（隐式超管）或账号登录；账号按 `admin`/
  `operator`/`readonly` 三级鉴权，只读可查看与导出、不能改，`user` 角色
  不能进入（2026-10-28，P2-23）。公网部署仍必须依赖 TLS 与非空
  `--server-key`，页面不提供操作审批。

### DEV-11 多查看者并发会话（2026-11-05 完成）

同一主机可同时接纳多个查看者。`HostSettings::max_viewers`（`host.ini`，
1..8，默认 2）映射到 `QuicServerConfig::max_clients`：上限在 TLS 完成前
执行，超出的连接立即拒绝；每个通过上限的连接由 `accept()` 交给独立的
`HostServer` 工作线程，拥有自己的 Hello、审批、权限、流和审计记录，共享
安全策略、证书注册、监听器和 TCP 载体。`max_viewers=1` 保留原有串行
语义。

- **共享桌面流**：DXGI 同一输出只允许一个 `IDXOutputDuplication`，因此
  首个桌面查看者是发布者，负责采集、编码、系统音频、光标与隐私遮罩，并把
  已编码访问单元、音频包、光标更新和桌面状态广播给跟随者。广播走
  `send_frame_nowait()`（队列满即丢该查看者的帧），慢查看者不会拖住采集
  循环。跟随者在自己的连接上处理输入、剪贴板、聊天、文件、终端、端口转发、
  摄像头、麦克风和 SAS；`StreamInfo` 变化用 `refresh_stream()` 更新。
  发布者离开后一个跟随者接管采集/编码/音频，接续已宣告的流而不重新
  Hello；注册表版本号单调递增且不因接管重置。
- **控制租约**：输入仍只有一个所有者。后来的桌面查看者以只读加入；租约在
  离开或输入被撤销时释放。新增 `QuicSession::set_permission_ceiling()`
  在流宣告后把“后续可授予”的上限恢复到审批掩码（仍受配置硬门限裁剪），
  但不改变当前 HelloAck 掩码，因此只读查看者可在租约释放后由操作员授予
  输入，且不会超出审批范围。隐私遮罩、显示切换/模式、流参数等主机级操作
  归发布者；跟随者的请求以 Busy/Denied 明确拒绝，关键帧请求转发给发布者。
- **审计与设置**：每个查看者按自己的 viewer ref 记录；重复引用由既有的
  host-generated 回退 ID 区分。`max_viewers` 越界值回落默认并在加载时告警。
  设置来回读写加入 `chast-host-settings-test`。

### DEV-12 出站 SOCKS5/HTTP(S) 代理（2026-11-05 完成）

查看器与主机的会合控制面、中继 TCP 载体和共享载体都可以走一个显式配置的

  入站 UDP 监听和局域网直连不变。
- **查看器 agent 与 Dart**：`--proxy`/`--proxy-stdin`（代理 URL 走 stdin，
  不进入 argv）；`ViewerConfig.Proxy` 下跳过 UPnP、UDP 中继与打洞，强制

  “outbound proxy needs the server's TCP carrier…”，不会回退直连。
  `server.json` 在密钥或代理非空时整体 DPAPI 保护，代理凭据不落明文；
  设置页新增“出站代理（可选）”；服务器身份校验、账号/地址簿、录制上传

### DEV-13 语音通话（主机麦克风上行）（2026-11-05 完成）

查看器可以发起一通“语音通话”，由主机打开麦克风并把 Opus 音频送回查看器
播放；协议从 v36 提升到 v37。没有新增 QUIC 流，呼叫协商与语音包都走已有
的可靠控制流：

- **协议**：新增 `VoiceCallRequest`（52，u8 标志 + u64 请求号，bit0 为
  连接/断开）、`VoiceCallResponse`（53，u64 请求号、结果码、原因，成功时
  附 Opus 编解码参数与 ≤64 字节 extradata）和 `VoiceAudio`（54，48 字节
  `AudioHeader` + Opus 包）。结果码为 Ok/Refused/Busy/Failed；原因字符串
  上限 256 字节。VoiceAudio 对编解码、采样率、声道、帧长、payload 长度与
  CRC 全部校验，非法包丢弃而不会交给解码器。
- **权限**：复用 `kPermissionMicrophone`（0x10）。主机未授权时立即回
  Refused；本连接已有通话回 Busy；采集启动失败回 Failed。运行中撤销麦克风
  权限会在两侧结束通话：主机停采集并下发停止，查看器停止播放并记录
  “主机结束了语音通话”。
- **主机中继**：每个 `HostServer` 工作线程独立服务自己查看者的通话，发布
  者与跟随者都可用。收到请求时通过 `HostServerConfig::voice_capture`
  （测试注入）或默认通信设备创建 `IMicrophoneCapture`，以采集器信息回
  Ok，然后按 `take_packet` 逐包发送 `VoiceAudio`；发送失败计入
  `voice_call_dropped`。关闭、权限撤销或采集失败都会停止并释放设备。新增
  统计 `voice_call_active/requests/accepted/completed/packets/bytes/
  dropped/errors`。
- **查看器**：`ViewerEngine::SetVoiceCall` 在授权时发起/结束通话；成功后
  用响应中的编解码参数创建 `IAudioDecoder` 与 `IAudioPlayer`（沿用系统
  默认输出或已固定的输出端点，到达即播），解码块送入播放器；播放器端点
  错误或主机停止时整条管线停止。状态经桥接发布为
  `voiceAuthorized/voiceEnabled/voicePending/voicePackets/voiceDropped/
  voiceErrors/voiceError`，会话工具栏新增通话按钮（不可用时置灰，接通中

### DEV-18 独立终端 / 摄像头 / TCP 隧道会话（2026-11-05 完成）

协议从 v40 提升到 v41：`SessionMode` 增加 `Terminal=2`、`Camera=3`、
`PortForward=4`；HelloAck/StreamInfo 在权限掩码之后追加一个 mode 字节；
新增标志 `kServerInfoControlOnly`（0x2000）表示会话没有桌面画面。解析器
强制 mode 与 files-only/control-only 一致，控制型会话不得携带画面、音频、
合并布局或显示器列表，权限掩码只能保留该模式对应的一个位。

- **主机策略**：`HostSecurity` 按 mode 把协商权限裁剪到单个能力位
  （Terminal→终端、Camera→摄像头、PortForward→端口转发）；未开启对应
  `allow_*` 时在握手阶段回明确的拒绝原因。Desktop 的权限路径不变。
- **主机派发**：`HostServer::serve_current_session` 把三种控制型会话交给
  新的 `control_session`，`announce()` 不打开视频/音频流，也不创建采集器
  或编码器；循环只泵 `TerminalRelay`/`CameraRelay`/`PortForwardRelay`。
  桌面专有请求（主机动作、OS 登录、会话列表/切换）一律回明确的拒绝，
  避免查看器空等；控制型会话不进入多查看者 publisher/follower 注册。
- **查看器引擎**：`Start`/`Run` 增加 `session_mode`，状态新增
  `control_only` 与 `session_mode`。无画面会话跳过解码器、GPU sink 和帧
  停滞检查，HelloAck 后直接进入 streaming，终端/摄像头/端口转发面板才能
  工作；摄像头画面仍走既有的零拷贝 GPU 纹理。
- **查看器界面**：设备卡片与最近连接菜单新增“远程终端”“主机摄像头”
  “端口转发”。独立会话页只有模式标题栏和对应面板：终端面板挂载即自动
  打开；摄像头面板自动注册纹理、列出设备并启动默认摄像头；端口转发在
  会话可用后弹出一次目标配置对话框，之后保留状态卡片（更换目标/停止）。
- **协议拒绝路径**：mode 与标志不一致、控制型会话带画面/音频/合并布局、
  权限掩码超出模式位、未知 mode 字节都会使 HelloAck 解析失败。

HelloAck 的 mode/control_only 一致性、无画面无媒体、权限裁剪、未知 mode

## 约束与注意事项

- 不要改动用户真实的 `%APPDATA%\chast\host.ini`；主机回环测试使用
  `build/*.ini` 隔离配置。
- 音频编码使用 vcpkg 安装的独立 Opus，不使用 FFmpeg 自带 Opus。
- 避免全仓 `gofmt` / `dart format` 造成无关改动；只格式化本次触及的文件。
- 不提交 `server/chast-server-identity.key`、`build/` 产物、dump 或测试私密配置。
- 协议字段只增不改；每次语义变化提升协议版本，保持 ALPN 家族名不变。
