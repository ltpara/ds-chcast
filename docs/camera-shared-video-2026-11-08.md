# 摄像头共享视频服务与协商

开发与验证：2026-11-08；记录整理：2026-11-09。参考 `D:/rustdesk-ref` 固定提交 `7423dced37845c48093b6f71bd82e4a16cc8c79d`，不是与最新发行版比较。

## 已实现

- 摄像头按 Media Foundation symbolic link 建立共享视频源。同一设备的多个观看者复用采集、D3D11 上传纹理和编码器，枚举序号只用于回答该连接收到的设备列表。
- 桌面附带摄像头复用连接已有的 `CodecPeer`：一个连接只有一票。摄像头专用会话开流时加入全局能力交集和偏好投票，停止、撤权、启动失败或断线时释放参与者。未开启摄像头的控制连接不限制其他视频源。
- 所有活动视频源共同证明候选格式可编码并产生 IDR 后再提交。摄像头 Start 成功也必须先取得实际 IDR；不兼容的观看者不会修改现有已提交格式。CCAM 帧头携带实际格式和尺寸，原生查看器已有对应的解码器重建路径，不增加线协议字段。
- 摄像头专用会话支持运行中编码偏好、FPS 和画质修改。工作线程处理协商，主机会话线程发送结果；未出首帧或前一请求未完成时返回 Busy。回复包含协商后的实际格式和当时编码 FPS；接受的选项保留到同一连接的下一次摄像头启动。
- 摄像头独立参与共享质量策略；桌面附带摄像头沿用桌面的质量参与者。共享编码 FPS 受设备实际协商帧率限制，避免按高于摄像头供帧率的预算编码。
- Camera-only 的零 LUID 选择默认硬件适配器，创建失败时尝试 WARP。显式非零 LUID 仍要求对应适配器。默认适配器在恢复时发生变化不会改变摄像头设备身份。
- 摄像头复用已有 Auto 编码恢复：普通硬编连续三次失败后，仅故障源切软件 VP9（2026-11-12 晚起；此前为软件 H.264/OpenH264），并重新计算全局兼容格式；健康桌面可保留硬编。设备失效仍重建采集。
- 摄像头转发队列维持最多 4 帧/4 MiB。队列或传输丢帧后清掉旧引用链并请求 IDR；停止/撤权后不再继续发送剩余队列。QUIC 发送边界额外拒绝接收端未声明支持的摄像头格式。
- 采集、编码、重建、销毁均在视频源的服务线程。摄像头 worker 只消费共享压缩帧；与桌面同时读取/更新同一连接偏好时，偏好读取也纳入协商事务锁。

实现入口：`src/capture/camera_capturer.cc`、`src/host/camera_relay.cc`、`src/host/desktop_stream.cc`、`src/host/host_server.cc`、`src/net/quic.cc`。

## 对照与边界

本地 RustDesk `src/server/video_service.rs` 的 `VideoSource::Camera` 复用视频服务，`src/server/connection.rs::update_codec_on_login()` 更新连接的全局解码能力。本项目已复用共享服务和连接投票，但摄像头专用连接在实际开流时才参加；停止后立即退出，生命周期与参考实现并非完全相同。

设备接口仍是 NV12/4:2:0；VP8/VP9、软件 AV1、I444 不在本次范围内。CCAM 继续使用自己的流和有限排队，并未获得桌面视频的应用取帧反馈窗口；摄像头专用连接的反馈驱动自适应仍有差异。驱动打开、编码、关闭等同步调用可能延长 worker 的停止等待，不能承诺驱动卡死时也立即退出。

本机没有枚举到物理摄像头，因此不将模拟媒体加真实 QUIC 的通过描述为真实摄像头采集/解码通过。USB 热插拔、不同厂商摄像头、不同显卡及多进程抢占仍需设备验收。

## 验证

复用既有 `host_parity`、`desktop_stream` 目标，没有新增 CMake 测试项目。`host_parity --camera` 使用可控媒体边界和真实 QUIC，验证：

1. 桌面加摄像头只计一票；多数票改变和退出恢复同时作用于两种视频源。
2. H.264-only 摄像头观看者约束 HEVC 桌面；多观看者复用一份摄像头管线。
3. 停止一位不影响其余观看者；停止最后一位受限观看者后，即使连接仍在线也恢复格式。
4. 无共同能力时开流失败且现有画面继续工作；首个摄像头画面是 IDR，帧头格式/尺寸正确。
5. 摄像头运行中硬编故障仅令摄像头切软件，采集不重建；撤销权限后资源在所属线程释放，桌面和音频继续。
6. Camera-only 在没有桌面采集时直接开流，修改偏好后实际 H.264 → HEVC；修改 FPS/画质、停止再启动、设备 12 FPS 上限约束。

验证结果：

- 主机、服务、QUIC 工具、原生 viewer probe 与既有两个测试目标构建通过：`build/camera-shared-verified-build.log`。最后补充 Camera-only 独立开流场景后，测试目标重建通过：`build/camera-shared-regression-build.log`。
- `host_parity` 通过（69.95 秒），`desktop_stream` 通过（4.42 秒）：`build/camera-shared-regression.log`。首轮与参数接入日志分别是 `build/camera-shared-test.log`、`build/camera-shared-options-test.log`。
- 平台临时程序实际调用 Media Foundation 枚举，设备数为 0；零 LUID 已成功创建 D3D11 设备，并到达预期的“打开不存在摄像头”错误，证明不再卡在指定显卡查找：`build/camera-platform-check.log`。
- 临时合成摄像头输出 322×242 NV12，使用产品 CameraCapturer 上传到真实 D3D11 的 336×256 补边纹理，再经实际 OpenH264 2.6.0 和解码器。可见亮度行位置、黑色补边、12 FPS 上限以及上传资源重建均通过：`build/camera-upload-check.log`。这验证上传及编解码链路，输入来自合成源，不能替代 Media Foundation 真实摄像头取帧。
- 临时验证程序位于忽略的 `build/`，未增加测试项目。保留已有 FFmpeg 类型转换、LIBCMT 链接及主机 `normalized` 遮蔽警告；未新增抑制选项。
